# Release 10.x.x

Version 10.x.x of the Data Space Connector contains a major change to the Keycloak deployment and to the OID4VCI realm model. They will be listed below, together with required actions for migration.

The two drivers of this release are:

1. **The Bitnami Keycloak Helm chart was withdrawn**, so the umbrella now depends on the [CloudPirates Keycloak chart](https://github.com/CloudPirates-io/helm-charts/tree/main/charts/keycloak). The CloudPirates chart targets the upstream Quarkus image (`quay.io/keycloak/keycloak`) and exposes a different `values.yaml` shape than Bitnami's, so the entire `keycloak:` configuration block must be rewritten.
2. **Keycloak 26.4 redesigned OID4VCI** ([keycloak/keycloak#39768](https://github.com/keycloak/keycloak/pull/39768)). The realm-attribute scheme `vc.<name>.*` and the `components.CredentialBuilder` block are gone; per-credential configuration moved to `ClientScope` attributes on scopes with `protocol: "oid4vc"`, and several mapper config keys were renamed or removed. The DSC chart's `realm.verifiableCredentials` API has been adjusted accordingly.

## 10.15.1 — OID4VP clients accept the verifier's own state

Since 6.24.2, the VCVerifier puts its own session id in the `state` of the authorization request,
instead of echoing the one the client sent. oid4vp-client-lib up to 0.0.6 rejected that request with
`Authorization request contains wrong state.`, so with the VCVerifier 6.27.0 of 10.15.0 no component
that authenticates through the library could obtain an access token from a verifier. That broke the
OID4VC contract negotiation of fdsc-edc, the order processing of contract-management in a central
marketplace, and the consent-facade's access to the provider's TM Forum APIs.

oid4vp-client-lib 0.0.7 no longer checks the `state`, and the following charts carry it:

| Chart | Version | Image |
|---|---|---|
| `fdsc-edc` | 0.7.6 → 0.7.8 | 1.8.4 → 1.8.5 |
| `contract-management` | 3.6.0 → 3.6.2 | 3.4.0 → 3.4.1 |
| `consent-facade` | 0.2.0 → 0.2.1 | 0.0.14 → 0.4.2 |

The `trust-anchor` chart moves its own `consent-facade` dependency, which the authority runs, to
0.2.1 as well. No configuration changes are needed. A deployment that sets its own image tag for one of these
components has to move it to the version in the table.

## 10.15.0 — The verifier's metrics move to their own port

The VCVerifier (6.27.0, chart `vcverifier` 4.17.0, through `vc-authentication` 1.5.2 and
`decentralized-iam` 2.1.28) now serves `/metrics`, and a copy of `/health`, on port 9090 of the
`verifier` Service (`metrics`), set with
`decentralizedIam.vcAuthentication.vcverifier.deployment.server.metricsPort`. Port 3000, which the
verifier's Ingress publishes, no longer answers `/metrics`, so the metrics are not reachable from
outside the cluster any more. `/metrics` also counts the requests to the API now; before, it counted
none of them.

### Breaking changes

- Anything that scraped the verifier's metrics on port 3000, or through its Ingress, has to scrape
  `verifier:9090/metrics` instead. To keep the metrics on the main port, set
  `decentralizedIam.vcAuthentication.vcverifier.deployment.server.metricsPort: 3000`.

The VCVerifier goes from 6.23.1 to 6.27.0, which also:

- accepts WebSocket upgrades only from the verifier's own origin, so a frontend on another origin
  can no longer open the login WebSocket;
- makes each login session single-use;
- verifies W3C Data Integrity proofs (`ecdsa-rdfc-2019`, `eddsa-rdfc-2022` and the JCS suites) in
  JSON-LD credentials.

The same release also brings, through `vc-authentication` 1.5.2: credentials-config-service 2.7.0,
dss-validation-service 0.1.0 and trusted-issuers-list 0.19.1. postgres-operator stays at 1.15.1.

## 10.14.0 — IdentityHub startup probe

IdentityHub now has a startup probe on its liveness endpoint, configured under
`identityhub.startupProbe` and enabled by default. It gives IdentityHub up to 5 minutes to start
(30 checks, every 10 seconds) before the liveness probe takes over.

Before, the liveness probe gave it about 35 seconds. When the node was busy starting the rest of
the release, IdentityHub was killed before it had started and went into a restart loop, and its
deployment could exceed its progress deadline. A restart in the middle of the first start could
also leave the `super-user` with an API key other than `identityhub.superuser.key`: IdentityHub
seeds the super-user only when it does not exist yet, so every call to the Identity API was
rejected with `401 Invalid API token`. To repair such a deployment, delete the `super-user`
participant context from the IdentityHub database and restart IdentityHub.

No action is required. Set `identityhub.startupProbe.enabled: false` to keep the previous
behaviour.

## 10.13.0 — EDC 0.18: fdsc-edc and IdentityHub move together

fdsc-edc moves to `1.8.x` (chart `0.7.x`), built on Eclipse EDC 0.18.1. The DCP wire contract
between the controlplane and IdentityHub changed in that range, so IdentityHub moves with it, to
`tractusx/identityhub:0.5.0-rc1` (EDC 0.18.0). An IdentityHub on EDC 0.14 does not work with the
new controlplane. The full list of fdsc-edc changes is in its
[release notes](https://github.com/SEAMWARE/fdsc-edc/blob/main/releases/notes/RELEASE_NOTES_EDC_0_18_1.md).

### Breaking changes

- The connector speaks DSP 2025/1 only. Counterparties still on DSP 2024/1 or 0.8 can no longer
  negotiate with it.
- The connector calls the counterparty's `/.well-known/dspace-version` without a token, and
  serves its own without one. A PEP in front of the DSP endpoint must not require a token on
  that path.
- The IdentityHub Identity API moves from `/api/identity/v1alpha` to `/api/identity/v1beta`, and
  its `{participantContextId}` path segment is the participant id URL-encoded once
  (`did%3Aweb%3Amp-operations.org`), no longer base64url. The participant creation payload
  carries `participantContextId` instead of `participantId`. The chart's bootstrap, rotation and
  credential-sync Jobs are updated; scripts of your own that call the Identity API must follow.
- IdentityHub needs one more datasource, `participantcontextconfig`, on the same database as the
  others. The chart configures it.
- The log formatter class of the IdentityHub image is now
  `org.eclipse.tractusx.monitor.formatter.ColorfulFormatter`. Values that override
  `identityhub.logging` with the old `org.eclipse.tractusx.identityhub.monitor.ColorfulFormatter`
  must be renamed.

### :warning: Required action: existing IdentityHub deployments

IdentityHub migrates its database by itself on start. Back up the database and the vault first:
going back means restoring both.

**IdentityHub's migrations do not carry existing rows forward**, so an upgraded deployment starts,
reports healthy and is unusable. Four tables are affected, and they surface one at a time — each
fix only reveals the next — so run all four statements in one go, after the first start on the new
image. Tracked upstream as
[tractusx-identityhub#371](https://github.com/eclipse-tractusx/tractusx-identityhub/issues/371).

```sql
-- 1. participant contexts have no configuration row: every authenticated Identity API call
--    returns 500 with `No configuration found for participant context super-user`
INSERT INTO edc_participant_context_config
  (participant_context_id, created_date, last_modified_date, entries, private_entries)
SELECT participant_context_id,
       (extract(epoch from now())*1000)::bigint,
       (extract(epoch from now())*1000)::bigint,
       '{}', '{}'
FROM participant_context
ON CONFLICT (participant_context_id) DO NOTHING;

-- 2. STS clients are not linked to their participant context (column defaults to ''):
--    POST /api/sts/token returns 500 with the same exception and an EMPTY context id
UPDATE edc_sts_client SET participant_context_id = id WHERE participant_context_id = '';

-- 3. key pairs have no usage (column defaults to '', but it holds a JSON array):
--    `MismatchedInputException: No content to map due to end-of-input` in SqlKeyPairResourceStore
UPDATE keypair_resource SET usage = '["sign_token","sign_presentation"]'
 WHERE usage = '' OR usage IS NULL;

-- 4. credential usage default is lower-case, the enum constant is not:
--    `No enum constant CredentialUsage.holder`
UPDATE credential_resource SET usage = 'Holder' WHERE usage = 'holder';
ALTER TABLE credential_resource ALTER COLUMN usage SET DEFAULT 'Holder';
```

Empty `entries` in (1) is enough; the row only has to exist. The bootstrap Job retries on its own
and completes once (1) and (2) are in place.

Then the DID document: it keeps the CredentialService endpoint it was published with, which carries
the participant id in base64url. The bootstrap Job does not rewrite it for a participant that
already exists, so every DCP presentation query against it returns `404`
(`Object of type IdentityHubParticipantContext with ID=<base64> was not found`) and the counterparty
reports a bare `401`. Either start IdentityHub on an empty database and vault, so the bootstrap Job
registers the participant again, or replace the endpoint.

`PATCH` is documented as the replace operation but **appends** on `0.5.0-rc1`, leaving two entries
with the same `id` — resolvers then pick the stale one and nothing appears to change. Delete and
re-add instead (the `{did}` segment of both calls stays base64url, while `{participantContextId}`
is URL-encoded):

```shell
DID=did:web:mp-operations.org
CTX=$(printf '%s' "$DID" | sed 's/:/%3A/g')
B64=$(printf '%s' "$DID" | base64 | tr '+/' '-_' | tr -d '=\n')

# removes every entry with that id, including the stale one
curl -X DELETE "${IDENTITY_API}/participants/${CTX}/dids/${B64}/endpoints?serviceId=credential-service&autoPublish=false" \
  -H "x-api-key: ${SUPERUSER_API_KEY}"

curl -X POST "${IDENTITY_API}/participants/${CTX}/dids/${B64}/endpoints?autoPublish=true" \
  -H "x-api-key: ${SUPERUSER_API_KEY}" -H 'Content-Type: application/json' \
  -d "{\"id\":\"credential-service\",\"type\":\"CredentialService\",\"serviceEndpoint\":\"${CREDENTIAL_SERVICE_URL}/api/credentials/v1/participants/${CTX}\"}"
```

Verify the published document ends up with exactly **one** `credential-service` entry, and that the
verification method still carries the same public key it had before the upgrade — if the key
changed, the bootstrap re-derived an identity and every counterparty's trust list is now stale.

## 10.12.0 — the chart's own values are validated

Helm used to accept any key in the values and ignore the ones nothing reads, so a typo, a renamed
value or one that no longer exists was silently dropped and the release came up without it. The
chart now ships a `values.schema.json`, and Helm validates the values against it on `install`,
`upgrade`, `template` and `lint`.

### What is validated

| Values | Validated by |
|---|---|
| This chart's own keys (`registration`, `identityhub`, `rainbow`, `statusListServer`, `vcCredentials`, `elsi`, `tracing`, `dataSpaceConfig`, `managedMongo`, `certManagerResources`, `consentManagement`, `issuance`, `extraManifests`, `nameOverride`, `fullnameOverride`, `imagePullSecrets`) | this chart's schema: unknown keys and wrong types are refused |
| Free-form maps under them (annotations, labels, node selectors, affinities, resources, security contexts, env maps, `identityhub.customCaCerts`, `managedMongo.spec`, `tracing.resourceAttributes`) | not validated: they take any key |
| A subchart's key (`keycloak`, `decentralizedIam`, `tm-forum-api`, `vault`, `marketplace`, `scorpio`, ...) | the subchart's own schema, if it ships one |
| `scorpio.ccs`, `tm-forum-api.registration` (removed in 10.11.0) | refused with a message naming their replacement |

### :warning: Required action: remove keys the chart does not know

A values file with a key this chart does not declare no longer renders:

```
Error: values don't meet the specifications of the schema(s) in the following chart(s):
data-space-connector:
- at '/registration': additional properties 'tyop' not allowed
```

Before upgrading, render your values against the new version and fix or remove what it reports:

```shell
helm template <release> <chart> --version 10.12.0 -f <your-values.yaml> > /dev/null
```

Every key reported was already ignored by the previous version, so removing it does not change the
deployment. Values files copied from the full `values.yaml` of an older release are the usual source,
in particular the registrations removed in 10.11.0 (`rainbow.ccs`, `scorpio.ccs`,
`tm-forum-api.registration`), which are refused even with `enabled: false`.

`helm install|upgrade|template --skip-schema-validation` (Helm 3.16 and later) skips the validation
as a stopgap.

### Values documented

Values the templates read but `values.yaml` did not list are now declared, with defaults that keep
the previous behaviour: `nameOverride`, `fullnameOverride`, `imagePullSecrets`, `elsi.keystore`,
`identityhub.didIngress.{className,annotations,hosts,tls}`, `rainbow.ingress.className` and
`vcCredentials.issuers`.

## 10.11.0 — safer defaults and a single way to register services at the verifier

A release with the umbrella's default values upgrades without any action. The breaking changes
below only concern releases that use the registrations at the verifier being removed, or rainbow.

### Breaking changes

| Change | Who is affected | Action |
|---|---|---|
| `scorpio.ccs` removed, with its `scorpio-registration` ConfigMap and the default `scorpio.additionalVolumes` entry that mounted it | releases that ran the registration script from their own init container in `scorpio.initContainers` | [move the service to the verifier's registration](#warning-required-action-register-services-through-the-verifier) and remove that init container - its ConfigMap is no longer rendered, so the pod would not start |
| `rainbow.ccs` removed, with the `register-credential-config` init container of the rainbow pod | releases with `rainbow.ccs.enabled: true` | [move the `tpp-service` to the verifier's registration](#warning-required-action-register-services-through-the-verifier) |
| `tm-forum-api.registration` removed, with its Job and ConfigMap | releases with `tm-forum-api.registration.enabled: true` (the previous default) | if the release relied on it, [move the service to the verifier's registration](#warning-required-action-register-services-through-the-verifier) - see below whether it ever registered anything |
| `contract-management.enableRainbow` defaults to `false` | releases with `rainbow.enabled: true` | set `contract-management.enableRainbow: true`; the chart refuses to render rainbow without it |
| `bae-did-secret` Secret removed | releases that referenced it by hand | nothing in the chart used it; it held a private key that was the same in every installation, so do not reuse it |

Keys that are no longer read are ignored, so values files that still set them render unchanged;
only the behaviour described above is gone.

### :warning: Required action: register services through the verifier

The umbrella had three registrations of its own at the verifier's credentials config API besides
the verifier's registration Job. They are gone; every service is registered with
`decentralizedIam.vcAuthentication.vcverifier.registration.services`, which is how all the
examples in `k3s/` already do it. Each entry is posted as is to the `/service` endpoint:

```yaml
decentralizedIam:
  vcAuthentication:
    vcverifier:
      registration:
        enabled: true
        services:
          - id: tmf-api                                  # was <component>.ccs.id
            defaultOidcScope: default                    # was <component>.ccs.defaultOidcScope.name
            oidcScopes:
              default:
                credentials:                             # one entry per former credentialTypes item
                  - type: VerifiableCredential
                    trustedParticipantsLists:
                      - https://tir.example.org          # was defaultOidcScope.trustedParticipantsLists
                    trustedIssuersLists:
                      - http://trusted-issuers-list:8080 # was defaultOidcScope.trustedIssuersLists
```

A former `oidcScopes` block written as a list of credentials per scope (`default: [ {type: ...} ]`)
becomes `default: {credentials: [ {type: ...} ]}` - the verifier only accepts the latter.

Like the removed registrations, the Job only creates services: one that already exists is left as
it is. A service registered by the old mechanism stays registered and needs no re-registration.

Whether the old registration did anything:

- `tm-forum-api.registration` never registered a service with `credentialTypes`, the key the values
  have documented since 9.x: it posted a body that is not valid JSON and the Job succeeded anyway.
  Only a release that set `ccs.oidcScopes` itself, in the `{credentials: [...]}` shape, got a
  service out of it.
- `scorpio.ccs` only rendered the script. Unless an init container running it was added to
  `scorpio.initContainers`, nothing was registered.
- `rainbow.ccs` ran on every start of the rainbow pod.

### Rainbow integration of contract management

The contract-management subchart enables its rainbow integration by default, while the umbrella
deploys no rainbow by default. Contract management then tried to register at a rainbow that did not
exist on every start and called it on every order. The integration now follows rainbow's default:

```yaml
rainbow:
  enabled: true
contract-management:
  enableRainbow: true   # required together with rainbow.enabled
```

### Other changes

These need no action:

- **APISIX gateway service:** `decentralizedIam.odrlAuthorization.apisix.service.externalTrafficPolicy`
  defaults to empty, so Kubernetes applies its own default - still `Cluster` for NodePort and
  LoadBalancer - and the service can be set to `ClusterIP`, which the apisix chart's `Cluster`
  default made the API server reject.
- **Verifier registration deadline:** `decentralizedIam.vcAuthentication.vcverifier.registration.job.activeDeadlineSeconds`
  is `1200`. The subchart's 300 seconds regularly ran out on a fresh install before the verifier
  was ready, failing the release.
- **Images:** the TM Forum API proxy uses `envoyproxy/envoy:distroless-v1.27.7`, which is what the
  floating `distroless-v1.27-latest` resolved to. Keycloak and the status-list-server, both pinned,
  use `imagePullPolicy: IfNotPresent`.
- **Trusted-issuers-list registration:** unchanged in behaviour - an issuer that is already
  registered is left as it is. The Job now says that changes to an existing issuer in the values do
  not reach the list; that takes the trusted-issuers-list API.

## 10.10.0 — eIDAS 2.0 validation moves into VCVerifier

The external `dss-validation-service` is no longer how eIDAS certificate chains are checked.
VCVerifier validates them itself, with PKIX chain building against a trust store it builds from the
EU List of Trusted Lists (ETSI TS 119 612). This release pins `decentralized-iam` **2.1.23 ->
2.1.25** (vcverifier subchart 4.15.3, VCVerifier 6.23.1). 10.9.0 already shipped 2.1.23, which
carries the validation itself but spells the LOTL override `lotUrl`

Full documentation: [eIDAS 2.0 Compliance](../deployment-integration/eidas/README.md).
Decision record: [ADR-0006](../adr/0006-eidas-validation-in-vcverifier.md).

### Off by default

```yaml
decentralizedIam:
  vcAuthentication:
    vcverifier:
      deployment:
        eidas:
          enabled: false
```

An existing release upgrades to a no-op. Nothing is fetched and no credential changes behaviour
until the block is switched on.

### Two mechanisms, different triggers

`eidas.enabled` builds the trust store. What then consults it depends on the issuer:

| Mechanism | Trigger | Covers | Formats |
|---|---|---|---|
| `did:elsi` proof check | `iss` is a `did:elsi:` DID | `x5c` chain + `organizationIdentifier` ↔ DID match | any |
| `EidasValidationService` | credential type carries `eidasConfig.enabled: true` | `x5c` chain + per-type `allowedCountries` / `requireQualified` | **SD-JWT only** |

A `did:elsi` deployment gets validation from `eidas.enabled` alone. A `did:web` or HTTPS issuer does
not: those resolve their key from the DID document or JWKS and the `x5c` header is ignored by the
proof check, so without `eidasConfig` on an SD-JWT type the trust lists are fetched on every refresh
and never consulted — with nothing failing to indicate it.

`eidasConfig` is also the only source of per-type country and qualified-service filters; the
`did:elsi` path searches all countries and applies no qualified filter.

### SD-JWT only

`EidasValidationService` is implemented for `dc+sd-jwt` and nothing else. A `jwt_vc_json` credential
with `eidasConfig.enabled: true` is rejected outright with `ErrorEidasSDJWTRequired` — not skipped.
This constraint applies to that mechanism only; the `did:elsi` proof check works for any format.

The shipped eIDAS overlay now issues `dc+sd-jwt` so that both mechanisms apply, and the DCQL query
matching them uses `meta.vct_values` (flat array) instead of `meta.type_values`.

### Breaking changes

| Change | Action |
|---|---|
| Maven profile `elsi` renamed to `eidas` | `mvn clean deploy -Plocal,elsi` → `-Plocal,eidas`. Maven does not fail on an unknown profile id, so the old invocation silently deploys without the overlay. |
| `k3s/provider-elsi.yaml` deleted, `k3s/consumer-elsi.yaml` renamed | Use `k3s/provider-eidas.yaml` / `k3s/consumer-eidas.yaml`. |
| `decentralizedIam.vcAuthentication.dss` deprecated | No effect once `eidas.enabled` is `true`. Remove it at your convenience. |
| `verifier.elsi.validationEndpoint` gone | Removed upstream in vcverifier 4.13.0; see the [Rollback](../deployment-integration/eidas/README.md#rollback) notes — reverting needs a dependency pin, not a values change. |

### `lotlUrl`, not `lotUrl`

Up to `decentralized-iam` 2.1.24 the vcverifier subchart declared the LOTL override as `lotUrl`
while the server read `lotlUrl`, so the subchart's own key was inert. 2.1.25 renames it, and there
is no backward-compatible alias: a values file that still sets

```yaml
decentralizedIam:
  vcAuthentication:
    vcverifier:
      deployment:
        eidas:
          lotUrl: "https://..."     # no longer a thing
```

is silently ignored and the verifier falls back to the official EU LOTL. Rename it to `lotlUrl`.
Deployments that already worked around this by setting `lotlUrl` need no change.

### Chart-side detail: `jades.enabled` is not a `vc.` attribute

`dsc.vcClientScopes` prefixes every credential attribute with `vc.`, which is right for Keycloak's
`CredentialScopeModel` but wrong for `jades.enabled` — the keycloak-jades-vc-issuer plugin reads
that one raw via `clientScope.getAttribute("jades.enabled")`. The template now keeps a small
pass-through list, `dsc.vcScopeUnprefixedAttributes`, so the documented override actually reaches
the plugin. Before this, setting `jades.enabled` had no effect at all.

## 10.8.0 — policies on the ServiceSpecifications a product is composed of

`contract-management` can now read the ODRL policies and the credential configuration from the
`ServiceSpecification`s a `ProductSpecification` is composed of, instead of only from the
`ProductSpecification` itself. An access policy protects an API, and an API is a
`ServiceSpecification` - so a provider composing one product out of three services can author three
policies where they belong, and an order for that product activates all of them.

### Off by default

```yaml
contract-management:
  enableSpecificationComposition: false
  specificationCompositionMaxDepth: 2
```

Enabling it changes **which configuration an order activates**, so it is opt-in per deployment. It
also adds one TMForum read per referenced `ServiceSpecification` to the activation of an order.

### What it does when enabled

| | |
|---|---|
| **Levels read** | the ordered `ProductSpecification`, the `ServiceSpecification`s it references, and recursively the `ProductSpecification`s it bundles. `ResourceSpecification`s are not read - they carry no connector configuration. |
| **Aggregation** | union, per level. Policies are de-duplicated by `odrl:uid`, credential configurations by value. Two *different* policies claiming one `odrl:uid` fail the activation, because the ODRL-PAP keys an installed policy by that uid. |
| **Credentials widen** | the trusted-issuers-list evaluates several configurations of one credential type as an OR, so a permissive part relaxes a restrictive one. Author with that in mind. |
| **One provider** | a composition that declares more than one provider fails the activation. A part that declares none inherits the composition's provider. |
| **Depth** | `specificationCompositionMaxDepth` levels; a deeper or cyclic composition is truncated and logged with a warning naming the specification, the skipped references and the limit. |
| **Broken references** | a referenced offering, specification, quote or provider that cannot be read now fails the activation with a logged error instead of activating nothing silently. |

### Fixed regardless of the flag

Three ways a *flat* order could already fail are gone:

- a `ProductSpecification` without any `productSpecCharacteristic`, or a characteristic without a
  `valueType`, raised a `NullPointerException` and took the whole order's activation down;
- an offering that bundles others instead of referencing a specification failed the activation of
  every other item in the same order;
- an order that legitimately configures nothing resolved to *nothing at all*, which the notification
  listener answered with a 404, which made the TMForum hub redeliver the event.

### Component versions

| Component | Version | Why |
|---|---|---|
| `contract-management` | chart **3.5.36** (app `3.3.12`) | reads the composed specifications and grants credentials under the id of the order that granted them |
| `trusted-issuers-list` | app **0.9.1** | the scope-addressed credential endpoints. `0.9.0` carries the API but does not start against MySQL, so `0.9.1` is the first usable release |

Both are delivered by the chart chain: `decentralized-iam 2.1.21` brings `trusted-issuers-list`
app `0.9.1` through `vc-authentication 1.3.7`, and the umbrella depends on `decentralized-iam
2.1.22`. No image override is needed.

### :warning: Behaviour change outside the flag

A single `ProductSpecification` that declares two **different** parties in the provider role now
fails the activation instead of picking one of them arbitrarily. Which contract-management is
responsible was never defined for that shape; refusing to guess is the safer reading. Check for
specifications with more than one `relatedParty` in the role configured as
`contract-management.organization.provider.role` before enabling.

## 10.4.0 — upstream Keycloak 26.7.0 and the realm-scoped keystore directory

The umbrella bumps the CloudPirates Keycloak chart from `0.21.7` to **`0.21.19`** and **drops the
`keycloak.image` override entirely**, so the deployment now runs the chart default —
upstream **`docker.io/keycloak/keycloak:26.7.0`** — instead of the SEAMWARE-patched
`quay.io/seamware/keycloak:26.6.3`.

| Removed (≤ 10.3.x) | New (10.4.0) |
|---|---|
| Chart `cloudpirates/keycloak 0.21.7` | Chart `cloudpirates/keycloak 0.21.19` |
| Image `quay.io/seamware/keycloak:26.6.3` (chart-level override) | Image `docker.io/keycloak/keycloak:26.7.0` (chart default, no override) |
| Keystore anywhere on the filesystem (e.g. `/did-material/cert.pfx`) | Keystore under `/opt/keycloak/data/<realm-name>/` |

The SEAMWARE fork existed only to carry the OID4VCI QR-endpoint fix
([keycloak/keycloak#44623](https://github.com/keycloak/keycloak/issues/44623)) and the Liquibase
changeset `26.7.0-verifiable-credential`. Both are upstream in 26.7.0, so the fork is no longer
needed and is no longer published as part of this chart.

### :warning: Required action: move the PKCS12 keystore under `data/<realm-name>`

Since **Keycloak 26.6.4** the `java-keystore` realm key provider may only read keystores from a
directory named after the realm, inside a fixed keystores root — by default
`${kc.home.dir}/data`, which is `/opt/keycloak/data` on the official image. For a realm called
`test-realm`, every keystore must live under `/opt/keycloak/data/test-realm`. Keystores outside
that boundary keep working for a read-only startup, but any create or update on the key provider
fails. See the [Keycloak upgrading guide](https://www.keycloak.org/docs/latest/upgrading/index.html)
(26.6.4 migration notes).

Update the Keycloak container's mount **and** the `storePath` so both point inside the realm folder:

```yaml
keycloak:
  extraVolumeMounts:
    # directory name MUST equal keycloak.realm.name
    - mountPath: /opt/keycloak/data/test-realm      # was: /did-material
      name: did-material
    - mountPath: /opt/keycloak/data/import
      name: realms
  signingKey:
    storePath: /opt/keycloak/data/test-realm/cert.pfx   # was: /did-material/cert.pfx
```

The init container that builds the keystore can keep writing to its own mount of the same
`emptyDir` (`/did-material`) — only the Keycloak container's view of the file is constrained.

If you use a `did:elsi` issuer, apply the same move to the ELSI keystore:

```yaml
elsi:
  storePath: /opt/keycloak/data/test-realm/keystore.p12   # was: /trust-store/keystore.p12
```

Deployments that set neither `elsi` nor `keycloak.signingKey` rely on the chart's fallback signing
key; its default keystore path now renders as `/opt/keycloak/data/{{ .Values.keycloak.realm.name }}/cert.pfx`,
so only the mount path needs adjusting.

The keystores root can also be relocated with the provider option
`--spi-keys--java-keystore--keystores-path`, but the DSC chart does not set it.

### :warning: Required action: manual DB migration when upgrading from `26.6.3`

If your database was previously running the SEAMWARE-patched `quay.io/seamware/keycloak:26.6.3`
image, the upgrade to upstream `26.7.0` does **not** apply cleanly through Liquibase: `26.6.3`
already carried early, differently-named versions of the `user_ver_credential` /
`issued_ver_credential` schema changes that upstream `26.7.0` introduces under its own changeset
ids, so the changeset checksums no longer match on startup.

You must run the script at [`doc/scripts/migration_26.6.3_to_26.7.0.sql`](../scripts/migration_26.6.3_to_26.7.0.sql)
against that database to bring its `26.6.3` schema in line with what `26.7.0` expects (column
renames/type changes on `user_ver_credential` and `issued_ver_credential`, the `cluster_event`
composite primary key, and resetting the affected `databasechangelog` checksums so Liquibase
accepts them as already applied).

:warning: **Take a backup of the Keycloak database before running this script.** It alters
constraints and column types in place; if it fails partway through, restoring from backup is the
only way back to a consistent state. Run it once, directly against the Keycloak database, before
starting Keycloak on the `26.7.0` image.

This step only applies if you are coming from `26.6.3` — deployments already on `26.7.0` (or a
fresh install) must not run it.

## OID4VCI realm model rewrite

The realm-attribute scheme `realm.attributes vc.<name>.*` and the `components.CredentialBuilder` block are no longer recognised by KC 26.4+. Per-credential configuration is now declared once in `realm.verifiableCredentials.<name>`; the DSC chart renders one `ClientScope` per entry with `protocol: "oid4vc"` and the attributes attached to the scope itself.

Before (9.x):

```yaml
keycloak:
  realm:
    attributes: |
      "vc.user-credential.format": "jwt_vc",
      "vc.user-credential.scope": "UserCredential",
      "vc.user-credential.vct": "UserCredential",
      "vc.user-credential.credential_signing_alg_values_supported": "ES256"
    credentialBuilder:
      jwt-vc-builder:
        id: jwt-vc-builder
        name: jwt_vc
```

After (10.x):

```yaml
keycloak:
  realm:
    verifiableCredentials:
      user-credential:
        attributes:
          format: "jwt_vc_json"
          verifiable_credential_type: "UserCredential"
          credential_signing_alg: "ES256"
          credential_build_config.token_jws_type: "JWT"
        protocolMappers:
          - name: context-mapper
            protocol: oid4vc
            protocolMapper: oid4vc-context-mapper
            config:
              context: https://www.w3.org/2018/credentials/v1
          - name: email-mapper
            protocol: oid4vc
            protocolMapper: oid4vc-user-attribute-mapper
            config:
              claim.name: email
              userAttribute: email
```

The key under `verifiableCredentials` (`user-credential` above) is the ClientScope name — i.e. the value the wallet sends as `credential_configuration_id`. The realm-level `realm.credentialBuilder:` block is removed entirely (in KC 26.4+ credential builders are loaded via SPI service-loader, not declared per realm).

### Format strings rename

| Format | 9.x value | 10.x value |
|---|---|---|
| SD-JWT VC | `vc+sd-jwt` | `dc+sd-jwt` |
| JWT-VC JSON | `jwt_vc` | `jwt_vc_json` |

The source of truth is `core/src/main/java/org/keycloak/VCFormat.java` in the Keycloak repository. The same rename applies wherever the format string appears: `verifiableCredentials.<name>.attributes.format`, DCQL queries (`realm.verifiableCredentials.<name>.protocolMappers` configs that reference a format, and any DCQL configuration in `decentralizedIam.vcAuthentication.credentials-config-service.registration.services[].oidcScopes.*.dcql.credentials[].format`).

### Template auto-derivations (DSC chart)

The DSC `_realm.tpl` template fills in two ClientScope attributes when they are not set explicitly:

- **`vc.issuer_did`** — derived from `elsi.did` if `elsi.enabled: true`, else from `keycloak.issuerDid`, else `${DID}`. Sets the `iss` claim of every issued JWT VC.
- **`vc.supported_credential_types`** — defaults to the value of `vc.verifiable_credential_type`. Drives the `type` array of JWT-VC JSON credentials and the metadata `credential_definition.type`. Override it explicitly under `attributes` if you need a different value than the SD-JWT `vct`.

### Mapper config renames

| Mapper | Old key (9.x) | New key (10.x) |
|---|---|---|
| every mapper | `supportedCredentialTypes` | (removed; mapper membership is structural per scope) |
| `oid4vc-user-attribute-mapper`, `oid4vc-target-role-mapper`, `oid4vc-static-claim-mapper`, `oid4vc-generated-id-mapper`, `oid4vc-issued-at-time-claim-mapper` | `subjectProperty` | `claim.name` |
| `oid4vc-subject-id-mapper` | `subjectIdProperty` | `claim.name` (plus `userAttribute`) |
| `oid4vc-vc-type-mapper` | (whole mapper) | deprecated; set the scope attribute `vc.verifiable_credential_type` instead |

A mapper that previously listed several credential types in `supportedCredentialTypes` must now be declared once under each VC entry it should apply to. The mapper `name` must be unique within a single VC's `protocolMappers` list — suffixing the name with the VC key (`-uc`, `-lpc`, `-oc`, …) makes greps easier.

:warning: KC 26.4+ does not allow two `oid4vc-target-role-mapper` mappers with the same `claim.name` in the same scope. Pick one target per VC, or use distinct claim names — but be aware that downstream verifiers (FIWARE vcverifier, ODRL/OPA in this chart) look for `credentialSubject.roles[*].target` by default, so deviating from the `roles` claim name requires a matching policy update.

### SD-JWT red list

KC 26.4+ enforces a "red list" of standard claims that **must not** be undisclosed in a SD-JWT VC: `iss`, `iat`, `nbf`, `exp`, `cnf`, `vct`, `status` (source: `core/src/main/java/org/keycloak/sdjwt/DisclosureRedList.java`).

If you override `verifiableCredentials.<name>.attributes.credential_build_config.sd_jwt.visible_claims`, include those seven names alongside your domain-specific ones, otherwise issuance fails with `IllegalArgumentException: UndisclosedClaims contains red listed claim names`.

```yaml
keycloak:
  realm:
    verifiableCredentials:
      user-sd:
        attributes:
          format: "dc+sd-jwt"
          verifiable_credential_type: "LegalPersonCredential"
          credential_build_config.sd_jwt.visible_claims: "iss,iat,nbf,exp,cnf,vct,status,roles,email"
```

### New feature flags

KC main has split the original experimental OID4VCI feature flag into one base
flag plus two sub-features. **All three must be enabled** for the DSC's
issuance flow to work:

```yaml
keycloak:
  features:
    enabled:
      - oid4vc-vci
      - oid4vc-vci-preauth-code        # KC 26.4+: gates the pre-authorized_code grant
      - oid4vc-vci-rest-credential-offer  # KC main / SEAMWARE 26.6.3: gates /create-credential-offer
```

Without `oid4vc-vci-rest-credential-offer`, Keycloak answers any call to
`/protocol/oid4vc/create-credential-offer` with
`403 invalid_client: "REST credential offer functionality is not enabled"`.
The flag is defined in [`Profile.Feature.OID4VC_VCI_REST_CREDENTIAL_OFFER`](https://github.com/keycloak/keycloak/blob/main/common/src/main/java/org/keycloak/common/Profile.java)
and is consumed by `OID4VCIssuerEndpoint.checkRestCredentialOfferEnabled`. It
landed in upstream `main` together with the OID4VCI QR-generation fix and is
present in the patched `quay.io/seamware/keycloak:26.6.3` image shipped by the
umbrella, even though vanilla 26.6.2 does not carry it.

The umbrella ships these three defaults out of the box.

### Endpoint changes for custom wallets / scripts

If you have custom code that talks to the Keycloak OID4VCI endpoints, update it as follows:

| Step | Old (KC 26.3) | New (KC 26.4 → 26.6.2) | Newer (KC main / SEAMWARE-patched 26.6.3) |
|---|---|---|---|
| Request offer URI | `GET /protocol/oid4vc/credential-offer-uri?credential_configuration_id=X` | `GET /protocol/oid4vc/create-credential-offer?credential_configuration_id=X&pre_authorized=true` | same |
| Build offer URL | `${issuer}${nonce}` | `${issuer}/${nonce}` | same |
| `/credential` body | `{"credential_identifier":"X","format":"jwt_vc"}` | `{"credential_configuration_id":"X"}` | `{"credential_identifier":"<id-from-token-response>"}` |
| `/credential` response | `{"credential":"<jwt>"}` | `{"credentials":[{"credential":"<jwt>"}]}` | same |
| `credential_identifier` source | n/a (anything accepted) | n/a | **must** come from the `authorization_details[].credential_identifiers` array returned by `/token` after exchanging the pre-authorized code |

The `pre_authorized` query parameter on `/create-credential-offer` defaults to `false`, so it must be set explicitly to obtain the pre-authorized_code grant. The `format` field of `/credential` is no longer accepted as input — format selection happens by picking a `credential_configuration_id` whose configured `vc.format` matches what the caller expects.

#### `credential_identifier` flow ([keycloak/keycloak#47404](https://github.com/keycloak/keycloak/pull/47404))

The patched 26.6.3 image arrives with the upstream rule that `/credential` only accepts a `credential_identifier`, never a `credential_configuration_id`. The identifier is short-lived and bound to the issued access token:

1. Wallet exchanges the pre-authorized code at `/token`.
2. `/token` response contains:
   ```json
   "authorization_details": [{
     "type": "openid_credential",
     "credential_configuration_id": "user-credential",
     "credential_identifiers": ["user-credential_0000"]
   }]
   ```
3. Wallet POSTs `/credential` with `{"credential_identifier": "user-credential_0000"}`.

Sending the legacy `{"credential_configuration_id": "..."}` body against this image returns `400 invalid_credential_request: "Credential must be requested by credential identifier from authorization_details: [...]"`.

The IT framework's `Wallet.java` was updated accordingly: it reads `authorization_details` off the `TokenResponse` model and falls back to the previous `credential_configuration_id`-based body when the field is absent, so it still works against older Keycloak versions.

### Client roles consistency

KC 26.4+ rejects user→client role assignments where the client itself does not declare the role. The realm import attempts to auto-create the missing role and, if multiple users assign it in the same batch, fails with `duplicate key violates unique constraint`.

:warning: Required action:

For every `clientRoles.<clientId>: [...]` you set on a user, declare the same role under `realm.clientRoles.<clientId>`. The `consumer.yaml` and `provider.yaml` example overlays in this repository show the consistent shape (`REPRESENTATIVE` declared on `did:web:mp-operations.org`, `seller`/`admin` declared on `did:web:fancy-marketplace.biz`).

### Per-user `verifiableCredentials` assignment

KC `main` (carried by the SEAMWARE-patched `26.6.3` image — see
[keycloak/keycloak@6ef5a79](https://github.com/keycloak/keycloak/commit/6ef5a79))
ties `/create-credential-offer` to a per-user `verifiableCredentials` list.
A user that has not been explicitly granted a credential gets:

```
400 invalid_credential_offer_request
"User 'X' does not have verifiable credential 'Y'."
```

even with a valid token and a properly configured ClientScope.

In the realm import JSON the list lives on each user entry:

```json
{
  "username": "employee",
  "verifiableCredentials": [
    { "credentialScopeName": "user-credential" },
    { "credentialScopeName": "operator-credential" }
  ]
}
```

:warning: Required action:

Either set this list per user, or set the chart flag below to have the
umbrella auto-assign **every** VC declared in the realm to **every** user
that has not provided its own `verifiableCredentials`:

```yaml
keycloak:
  realm:
    wallets:
      issueCredentialsToUsers: true
```

`wallets.enabled` does **not** need to be `true` for this to work — the
two flags are independent. The local k3s overlays (`k3s/consumer.yaml`,
`k3s/provider.yaml`) ship with `issueCredentialsToUsers: true` so the
example deployment works out of the box; in production you usually want
to declare the per-user lists explicitly instead.

## OID4VCI draft compliance

Keycloak 26.6.3 implements **[OID4VCI Draft 15](https://openid.net/specs/openid-4-verifiable-credential-issuance-1_0.html)**.
The 26.4 redesign ([keycloak/keycloak#39768](https://github.com/keycloak/keycloak/pull/39768)) explicitly aligned the
credential issuance flow with Draft 15: `CredentialSubject` was removed from `CredentialDefinition`, the `format`
field was dropped from `CredentialRequest`, the metadata endpoint claims structure was rewritten and the `cwt` proof
type was removed.

Practical implications already covered above (see *Endpoint changes for custom wallets / scripts*, *OID4VCI realm model
rewrite* and *Format strings rename*):

- `/credential` request: send `credential_configuration_id` (no `format`); response is `{"credentials":[…]}`.
- `/credential-offer-uri` is replaced by `/create-credential-offer?pre_authorized=true`.
- Format strings updated: `jwt_vc` → `jwt_vc_json`, `vc+sd-jwt` → `dc+sd-jwt`.

If you maintain a custom wallet or test harness, target Draft 15 endpoints and payloads.

## Credential request/response encryption (JWE)

Keycloak 26.6.x advertises OID4VCI credential encryption in the issuer metadata
(`/.well-known/openid-credential-issuer`). Two independent features are involved, and both have
caused interop failures with wallets that encrypt:

**Request encryption (`credential_request_encryption`).** Advertised whenever the realm has an
asymmetric encryption key — the chart ships one via the `ecdh-generated` key provider in
`keycloak.realm.defaultKeyProviders` (ECDH-ES, P-256). A wallet that encrypts the `/credential`
request must include the issuer key's `kid` in the JWE header; otherwise Keycloak answers
`400 invalid_encryption_parameters` with `Request has JWT content-type but is not a valid JWE:
Missing kid in JWE header`. The EUDI `eudi-lib-ios-openid4vci-swift` omitted the `kid` before
**0.38.3** (fixed by *"add kid to header on issuance"*).

**Response encryption (`credential_response_encryption`).** Advertised whenever the realm has *any*
asymmetric key — if the `ecdh-generated` key is removed it simply falls back to `RSA-OAEP` via the
realm's RSA token-signing key. A wallet requesting an encrypted response must **not** send `alg` at
the top level of the `credential_response_encryption` object: Keycloak's model only accepts
`{zip, enc, jwk}` and otherwise fails with `Unrecognized field "alg" (class
CredentialResponseEncryption)`. `eudi-lib-ios-openid4vci-swift` sent the top-level `alg` before
**0.40.0** (fixed by *"Remove alg from top level"*).

Guidance:

- Wallets that opt into encryption need **`eudi-lib-ios-openid4vci-swift` ≥ 0.40.0** (carries both
  fixes). Lissi does not encrypt the request/response, so it is unaffected.
- There is **no realm/chart toggle** to stop advertising `credential_response_encryption`: it is
  inherent to KC 26.6.x and the RSA signing key cannot be removed. Removing the `ecdh-generated` key
  provider only neutralises **request** encryption (the section disappears from the metadata);
  response encryption stays advertised but is optional (`encryption_required: false`), so a wallet
  that does not request it is unaffected.

## Operational notes & gotchas

### Reusing an existing Keycloak database (USER_VER_CREDENTIAL migration)

The post-26.4 OID4VCI model ties `/create-credential-offer` to a per-user `verifiableCredentials`
list, backed by a custom `USER_VER_CREDENTIAL` table. Pointing 26.6.x at a database created by an
older Keycloak fails at offer time with:

```
ERROR: column uvce1_0.version does not exist
  at org.keycloak.protocol.oid4vc.utils.OID4VCUtil.hasVerifiableCredential
```

The shipped `quay.io/seamware/keycloak:26.6.3` image carries the Liquibase changeset
`26.7.0-verifiable-credential`, which adds the missing `version` column on startup. Use 26.6.3 (not
26.6.2) when reusing a database.

Related: Keycloak **does not re-import an already-existing realm**. Changes under `keycloak.realm.*`
do not take effect on a running realm — delete and recreate the realm (the external DB makes this
safe) for the new import to apply.

### DCQL query format gotchas

For Credentials Config Service / VCVerifier scopes that use DCQL (`oidcScopes.<scope>.dcql`):

- **`meta.type_values`** (W3C `jwt_vc_json`) is an **array of string arrays**, e.g.
  `[["MarketplaceCredential"]]` — a flat array is rejected with
  `cannot unmarshal string into ... type_values of type []string`.
- **`meta.vct_values`** (SD-JWT `dc+sd-jwt` / `vc+sd-jwt`) is a **flat array of strings**, e.g.
  `["LegalPersonCredential"]`.
- **`credential_sets`** must be a non-empty array. A nil `credential_sets` serialises to JSON `null`,
  which the SwiftyJSON parser in the Lissi/EUDI wallets rejects with "JSON is invalid". For
  dual-format offers, list both credential ids as alternatives:
  `credential_sets: [{ options: [["lpc-dc-sd-jwt"], ["lpc-vc-sd-jwt"]], required: true }]`.

### StatefulSet recreation when upgrading from 9.x (Bitnami → CloudPirates)

The Bitnami and CloudPirates keycloak charts both name the workload `<release>-keycloak`, but their
StatefulSet specs differ in immutable fields (`serviceName`, `selector`, `volumeClaimTemplates`). An
in-place upgrade fails with `updates to statefulset spec for fields other than ... are forbidden`.
Delete the old StatefulSet so it is recreated — `kubectl delete statefulset <release>-keycloak`
(the external Postgres means no data loss; the pod is stateless).

## Migration checklist

1. Apply the value renames in the table above to your `keycloak:` block; remove the listed obsolete keys.
2. Rewrite each entry under `keycloak.realm.attributes` of the form `vc.<name>.*` as a `keycloak.realm.verifiableCredentials.<name>` block with `attributes` and `protocolMappers`. Drop the `keycloak.realm.credentialBuilder:` block entirely.
3. Update format strings: `vc+sd-jwt` → `dc+sd-jwt`, `jwt_vc` → `jwt_vc_json`, both in the realm config and in any DCQL queries you maintain.
4. If you override `keycloak.realm.defaultClients`, preserve `account-console.attributes.oid4vci.enabled: "true"`.
5. Add `oid4vc-vci-preauth-code` to `keycloak.features.enabled`.
6. Update any custom `wait-for-keycloak` probe to target `<release>-keycloak-metrics:9000`.
7. Validate locally with `helm template charts/data-space-connector -f your-values.yaml` and a one-off `kc.sh import --dir=/opt/keycloak/data/import` against a 26.6.3 pod before redeploying.
8. Rerun your integration tests; confirm both consumer and provider Keycloaks reach `Listening on http://0.0.0.0:8080` and that VC issuance flows complete.

For a worked end-to-end example, see the migrated `k3s/consumer.yaml` and `k3s/provider.yaml` overlays shipped with this release; the [`oid4vc-protocol-mappers.md`](../keycloak/oid4vc-protocol-mappers.md) reference now documents the 26.6.3 mapper API.

identityhub:

## EDC / Dataspace Protocol production readiness

The EDC part of the chart could be deployed but not operated: everything that keeps a participant's
identity alive lived outside the chart, and several pieces broke on their own with no deployment
involved. This release closes that.

### Participant provisioning is part of the chart

A deployed identityhub used to be inert - no participant context, no signing key in Vault, no
credential - and the documented way to fix that was a `curl` sequence run from a workstation, which
every real deployment reimplemented as a hand-written Job. `identityhub.bootstrap` now performs it
in-cluster and idempotently, on install and on every upgrade.

| Key | Type | Default | Description |
|---|---|---|---|
| `identityhub.bootstrap.enabled` | bool | `false` | Provision the participant context from the chart |
| `identityhub.bootstrap.did` | string | `""` | DID of this participant |
| `identityhub.bootstrap.keyAlias` | string | `key-1` | Vault alias and DID fragment of the signing key |
| `identityhub.bootstrap.credentialServiceUrl` | string | `""` | Public base URL of the DCP credential service |
| `identityhub.bootstrap.identityKey.secretName` | string | `""` | Secret holding the identity private key |
| `identityhub.bootstrap.identityKey.algorithm` | string | `EC` | `EC` or `RSA` |
| `identityhub.bootstrap.stsClientSecret.existingSecret` | string | `""` | Secret holding the STS shared secret |
| `identityhub.bootstrap.kidCheck.enabled` | bool | `false` | Verify the issuer signs with `<did>#<keyAlias>` |
| `identityhub.bootstrap.credential.secretName` | string | `""` | Credential written by the vc-operator |
| `identityhub.bootstrap.rotation.enabled` | bool | `false` | Render the signing-key rotation Job |

`post-upgrade` is part of the default hook and needs to stay there while Vault runs in dev mode: its
storage is in-memory, so every Vault restart drops the signing key, the super-user credential and the
STS client secret, and only a re-run restores them.

### The identityhub credential no longer goes stale on its own

The identityhub holds its own copy of the credential a connector presents, and nothing kept it in
step: the vc-operator renewed the Secret while the identityhub went on presenting the previous
credential until it expired, taking the DCP lane down with a Secret that looked perfectly healthy.

`identityhub.credentialSync.enabled` renders a sidecar in the identityhub pod that mirrors the Secret
the vc-operator maintains into the identityhub's credential store, on issuance and on every renewal.
It needs the Secret's name (`identityhub.credentialSync.secretName`) and the super-user api key in a
Secret (`identityhub.superuser.existingSecret`).

The sidecar writes over `localhost`: the Identity API is component-internal, so the only thing that
writes to it is the pod that owns the store. Obtaining and renewing the credential stays with the
vc-operator, which never talks to the identityhub.

`identityhub.bootstrap.credential.*` is deprecated in favour of it and still read as a default:
storing the credential is not a bootstrap concern, since a Job that only runs on install and upgrade
leaves the copy stale after the first unattended renewal. The bootstrap Job no longer stores it.

Related: `identityhub.credentialWatchdog.checkPeriodSeconds` now exposes the identityhub's own
watchdog, which re-requests expiring credentials from a DCP issuer service. It defaults to `0`
(off), because the credentials here come from an OID4VCI issuer and there is no issuer service to
ask; upstream defaults it to 60 seconds with a one-week renewal grace period, which for a credential
that only lives a week means it is considered renewable from the moment it is issued.

Also consider raising `renewBefore` from the `5m` default: five minutes leaves no room to notice a
failure before the credential in use expires.

### Vault can keep its state across restarts

| Key | Type | Default | Description |
|---|---|---|---|
| `vault.hashicorp.existingSecret` | string | `""` | Secret holding the Vault token, instead of a plaintext value |
| `vault.hashicorp.existingSecretTokenKey` | string | `token` | Key within that Secret |
| `vault.unattended.enabled` | bool | `false` | Persistent Vault, initialised and unsealed by the chart |
| `vault.unattended.autoUnseal` | bool | `true` | Unseal automatically; `false` means unsealing by hand |
| `vault.unattended.secretShares` / `.secretThreshold` | int | `1` / `1` | Shamir split of the master key |
| `vault.unattended.secretName` | string | `vault-unseal-keys` | Secret the unseal keys are written to |
| `vault.unattended.provisionToken` | bool | `true` | Mint the token the components use, and its ACL policy |
| `vault.unattended.tokenPeriod` | string | `768h` | Period of that token; renewed by EDC in process |
| `vault.unattended.tokenPolicyName` | string | `dsc-connector` | Name of the policy created for it |

`vault.hashicorp.token` is rendered into ConfigMaps in clear, so anyone able to read ConfigMaps in the
namespace can read the credential that unlocks the participant's signing key. With `existingSecret`
the identityhub receives it as `EDC_VAULT_HASHICORP_TOKEN` and the property is omitted from the
ConfigMap entirely.

A Vault with persistent storage comes back sealed after every restart, so persistence alone is not
enough; `vault.unattended` initialises an empty Vault once and unseals it whenever it finds it sealed,
and mints the scoped token the components authenticate with.

**The name is deliberate: this is not a production security posture.** A Vault that unseals itself
keeps its unseal keys in a Secret of the same namespace, so whoever can read Secrets there can open
it. It is the right trade for demo and staging, where the alternative - dev mode - loses the
participant's identity on every restart and does not put it back until the next deploy, because the
bootstrap Job is a Helm hook and not a restart hook.

Production is `autoUnseal: false`: no unsealer is deployed, the operating organisation holds the key
shares, and a quorum unseals on every start. That step cannot be automated away. Both variants,
including the one-off init and the per-start procedure, are in
[the production guide](../deployment-integration/production/VAULT.md).

`vault.unattended.enabled` refuses to render next to `vault.server.dev.enabled` rather than quietly
doing nothing.

### Rotating the signing key

`identityhub.bootstrap.rotation` replaces the identity key while keeping the same Vault alias and the
same DID fragment, which is what keeps the Keycloak realm out of it - `signing_key_id` is a
ClientScope attribute and cannot be changed by automation on an existing realm.

:warning: There is no overlap window. The moment the key is replaced, everything signed with the
previous one under that fragment stops verifying, credentials already in wallets included, so
re-issuance is part of the operation. The Job is opt-in and never a Helm hook. The runbook is in the
production guide.

Note also that cert-manager's `privateKey.rotationPolicy` defaults to `Always` since cert-manager
1.18, i.e. renewing a certificate generates a new key, which invalidates the published DID document.
Declare `rotationPolicy: Never` explicitly for the identity key.

### Changed defaults

| Key | Old | New | Why |
|---|---|---|---|
| `fdsc-edc.common.config.tmfExtension.enabled` | `true` | `false` | It shipped enabled with seven empty addresses, and `TMFConfig` converts them with `URI.create(...).toURL()` at boot, so the default configuration aborted startup with `URI is not absolute`. Enabling it requires all seven. |
| `fdsc-edc.common.config.oid4vp.trustAll` | `true` | `false` | Disabling TLS verification is not a safe default. |
| `fdsc-edc.common.config.edc.log.level` | `DEBUG` | `INFO` | DEBUG logs every DSP message, token contents included. |
| `registration.annotations["helm.sh/hook"]` | `post-install` | `post-install,post-upgrade` | With post-install only, a release that already exists never re-registers, so nothing added to `registration.issuer` after the first install ever reached the trusted-issuers list. |

:warning: Required action: if you relied on `tmfExtension` being enabled by default, set
`fdsc-edc.common.config.tmfExtension.enabled: true` explicitly. The `k3s/dsp-*.yaml` values in this
repository were updated the same way.

This matters beyond TMForum, and the symptom points nowhere near it. The extension is what
registers the connector's `ObjectMapper`, imperatively, at the end of
`TMFContractNegotiationExtension.initialize()` - which returns early when disabled. Several
extensions inject one, so with TMF off the boot dies at whichever of them comes first, usually
`OID4VPExtension`:

```
No default provider for required injection point Field "objectMapper"
  of type [class com.fasterxml.jackson.databind.ObjectMapper]
```

Any deployment using the OID4VP lane needs `tmfExtension.enabled: true` and all seven addresses.

### Fixes

* `vc.expiry_in_seconds` and `vc.refresh_interval_in_seconds` are kept in sync. The admin console
  shows the first while the issued `exp` comes from the second, so setting only one produced
  credentials expiring at a completely different time than the console claimed - with Keycloak's
  default, a week instead of whatever was configured. Setting neither still leaves Keycloak's
  defaults alone.
* `vc.signing_key_id` defaults to the key id the DID document publishes when the identityhub serves
  that document. Keycloak otherwise defaults it to the bare DID, which is not resolvable there, and
  issuance fails with `No key for id '<did>' and algorithm ... available`.
* The trusted-issuers registration script treats a 409 as success. It used `curl -f`, so an
  already-registered issuer failed the Job - which is why making it run on upgrade required this
  fix first.
* `identityhub.customCaCerts` works. The deployment mounted an empty `emptyDir` over the JVM
  truststore and referenced a ConfigMap nothing created, so declaring extra CAs replaced the whole
  truststore with nothing. An init container now imports them into a copy of it.
* `identityhub.customCaCertsFrom` takes CAs from Secrets and ConfigMaps that already exist, so a
  cert-manager Secret can be pointed at instead of having its PEM copied into values. Sources are
  merged with a projected volume and a deployment that uses only this key renders no ConfigMap at
  all. Secrets default to `ca.crt`: mounting a `kubernetes.io/tls` Secret whole would put `tls.key`
  in the pod and fail the import.
* `identityhub.logging.persistence` is gone. It mounted a claim that nothing created, so enabling
  it produced a pod that could never be scheduled. Rather than add the missing claim, the option was
  removed: the file handler writes to an `emptyDir` and the console handler is what feeds the
  cluster's log stack, which is where logs belong.
* The identityhub service exposes the `accounts` port (8085) that the deployment opens, so the STS
  Accounts API is reachable in-cluster.

### Tests

`helm unittest` gained suites covering the bootstrap, the credential-sync sidecar, the unattended
Vault surface and the holder key id cross-check, and
`.github/scripts/eval.sh` now renders each chart's `ci/*-values.yaml` in addition to its defaults.
Until now nothing in the EDC lane was linted or schema-validated at all, because it is all disabled
by default.

## Consent management

The connector can now record and enforce **consent** (ISO/IEC TS 27560) on a data path, opt-in via the
`consent` maven profile. A data subject's personal data is released to a consumer only while that
subject has a granted consent for it.

Three components carry it, each deployed from its own published FIWARE chart:

| component | chart | runs at |
|---|---|---|
| consent-manager | `oci://quay.io/fiware/helm-charts/consent-manager` | the authority (`trust-anchor` release) |
| consent-facade | `oci://quay.io/fiware/helm-charts/consent-facade` | the authority, plus a provider-local instance |
| consent-owner-resolver | `oci://quay.io/fiware/helm-charts/consent-owner-resolver` | the provider |

Enforcement itself is an APISIX external plugin (`consent-filter`) on the provider's
`mp-data-service-consent` route: OPA authorizes the request on the presented *credential*, then the
plugin asks the owner-resolver whose data was returned and checks that owner's consent at the
consent-manager - so the decision is made from the data, not from whoever requested it.

Participants and data subjects authenticate over **OID4VP** throughout; no component holds a
participant client secret, and the shared consent key is injected by the authority's APISIX facade
rather than handed to callers.

See [Consent Management](../CONSENT_MANAGEMENT.md) for the architecture, the enabling overlays and two
end-to-end walkthroughs.


## `contract-management` 3.3.12 requires `trusted-issuers-list` >= 0.9.0

`contract-management` now registers the credentials of a newly onboarded participant through
`PUT /issuer/{did}/credential?scope=<product-order-id>`, an endpoint that only exists from
`trusted-issuers-list` 0.9.0 on. Against an older list the call answers `404`, the issuer keeps its

Both charts therefore ship a list that serves it:

| chart | dependency | version | list |
|---|---|---|---|
| `data-space-connector` | `decentralized-iam` | 2.1.19 -> **2.1.21** | 0.8.1 -> **0.9.1** (via `vc-authentication` 1.3.7) |
| `trust-anchor` | `trusted-issuers-list` | 0.18.4 -> **0.18.7** | 0.8.1 -> **0.9.1** |

The `decentralized-iam` bump also raises `vcverifier` from 6.15.1 to **6.21.0** and
`odrl-authorization` stays at 2.4.1. If you run the list **outside** the chart
(`trusted-issuers-list.enabled: false`), raise your own deployment to >= 0.9.0 before upgrading.
