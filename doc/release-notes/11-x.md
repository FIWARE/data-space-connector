# Release 11.x.x

Version 11.x.x of the Data Space Connector replaces the consent-manager of the consent management
scenario. Changes will be listed below, together with the required actions for migration.

Only deployments that use consent management are affected: the data-space-connector chart loses one
value that no template read, while the breaking changes are in the trust-anchor chart and in the
consent-filter plugin.

## 11.0.0 — consent management moves to dsc-consent-manager

The consent-manager of the consent management scenario is replaced: the Prometheus-X service
(Node, MongoDB, a shared consent key, APISIX facade routes at the authority) gives way to
[dsc-consent-manager](https://github.com/SEAMWARE/dsc-consent-manager) (Java, PostgreSQL), which
validates the JWT of the authority's VCVerifier on every call. See
[ADR 0008](../adr/0008-dsc-consent-manager.md) and
[Consent Management](../CONSENT_MANAGEMENT.md), which also describes the
[migration](../CONSENT_MANAGEMENT.md#migrating-from-the-prometheus-x-consent-manager).

**The data-space-connector chart only loses one value:** `consentManagement.enabled`, which no
template ever read. The provider side is the `consent-facade` and `consent-owner-resolver`
subcharts plus the consent-plugin on the provider's APISIX, each with its own `enabled`. Drop the
key from your values - `values.schema.json` rejects what the chart does not declare. A provider that
does not use consent management has nothing to do.

The breaking changes for consent users are elsewhere:

- **trust-anchor chart 2.0.0** deploys `dsc-consent-manager` 0.1.0 under the unchanged
  `consent-manager` key, pinned to image **0.0.3** with
  `consent-manager.deployment.image.tag` because that chart's `appVersion` is still 0.0.1. The
  pin is required, not cosmetic. Before 0.0.3:
  - 0.0.1 answers every `POST /v1/privacy-notices/by-contract` with a 502 against a contract
    service that keeps only bilateral contracts - which the consent-facade is, since it answers
    the ecosystem endpoint with 501;
  - it cannot be exempted from a global HTTP proxy at all, because a client set to
    `proxy-type: DIRECT` inherits the global proxy address and then fails every request;
  - a contract party was identified by the participant identifier alone, while the
    consent-facade's `/verify` - the lookup the owner-resolver makes to find the governing
    contract - matches only the participants' self-description URLs. One agreement can carry
    only one form in `provider-id`/`consumer-id`, so notice generation and the consent gate
    could not both work: with DIDs every gated read was denied, with URLs generation answered
    `404 No active participant is registered under '<url>'`. 0.0.3 accepts either name
    (ADR-0017 of dsc-consent-manager), and the agreements this deployment writes carry the
    self-description URLs, as `contract-management` already did.

  Drop the pin once the dependency moves to a chart whose `appVersion` is 0.0.3 or newer.
  - The consent MongoDB and its values are gone. The service stores its data in the chart's
    Zalando `managedPostgres`, under a user and database both fixed to `consent_manager`. External
    Postgres is not supported.
  - The consent key is gone. Callers authenticate with a JWT of the VCVerifier service
    `consent-manager`, set with `consent-manager.identityProviders.primary`.
  - A setup Job (`consentManagement.setup`) copies the database credentials into
    `consent-manager-env` and generates the receipt signing key in `consent-manager-signing-keys`,
    once; it never rotates them. The database itself is created by the Zalando operator from
    `managedPostgres.config.databases`, on a fresh cluster and on an existing volume alike.
    `consentManagement.setup.resources` sizes its containers, and its ServiceAccount and RBAC can be
    managed outside the chart with `consentManagement.setup.serviceAccount.create` / `.name` and
    `consentManagement.setup.rbac.create`.
  - SMTP credentials come from `consentManagement.smtp.existingSecret`.
  - The consent-manager's NetworkPolicy admits its management port (9090) to
    `consentManagement.networkPolicy.metricsScrapers` only. Enabling
    `consent-manager.serviceMonitor` without listing the scraping Prometheus there drops every
    scrape.
  - The chart `fail`s on the removed values: `managedMongo`, `consentManagement.mongo`,
    `consent-manager.mongo`, `consent-manager.secret.consentKey`, `consent-manager.externalIdp`,
    `consent-manager.appEndpoint`, `consent-manager.contractService` and
    `consent-manager.secrets.smtpUser`/`smtpPassword`.
- **The provider's consent route needs consent-filter plugin 1.0.0**, which speaks only the `/v1`
  API, so the image and the route config change together. `consent_api_url` points at the
  consent-manager directly; there is no authority facade in between. `consent_api_host` and
  `consent_key` are removed. `check_mode`, `consumer_claim`, `require_purpose` and
  `require_contract` are new. Provider and consumer must both be registered participants at
  the consent-manager.

Consents stored in MongoDB are not migrated. Data subjects have to grant them again under the new
service.
