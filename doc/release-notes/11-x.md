# Release 11.x.x

Version 11.x.x of the Data Space Connector moves the DCP controlplane to fdsc-edc 2.x, which runs
one connector in several dataspaces, and replaces the consent-manager of the consent management
scenario. Changes will be listed below, together with the required actions for migration.

Two groups of deployments are affected:

- deployments with an fdsc-edc DCP controlplane (`controlplane-dcp`) must configure participant
  contexts and move to the v5beta management API, see
  [the first section](#1100--fdsc-edc-200-multi-dataspace-controlplane-dcp);
- deployments that use consent management: the data-space-connector chart loses one value that no
  template read, while the breaking changes are in the trust-anchor chart and in the
  consent-filter plugin.

A deployment with neither only gets the new fdsc-edc image on its `controlplane-oid4vc`, which
behaves as before.

## 11.0.0 — fdsc-edc 2.0.0: multi-dataspace controlplane-dcp

fdsc-edc moves to `2.x`, which runs `controlplane-dcp` as EDC virtual participant contexts: one
connector takes part in several dataspaces, each through its own DSP profiles. There is no legacy
mode. A DCP controlplane without `fdsc.participants.*` starts, but every DSP route returns 404.
`controlplane-oid4vc` has no functional change. The full list of changes is in the upstream
[release notes](https://github.com/SEAMWARE/fdsc-edc/blob/2.1.1/releases/notes/RELEASE_NOTES_MULTI_DATASPACE.md)
and [multi-dataspace guide](https://github.com/SEAMWARE/fdsc-edc/blob/2.1.1/docs/multi-dataspace.md).
The DSC side is described in [Multi-dataspace operation](../MULTI_DATASPACE.md).

**Image pin.** The chart deploys image `2.1.1`, the oldest 2.x the DSP flows work on. 2.0.0 serves
only the v5beta management API, which has no EDR endpoint, so a consumer cannot read the data
address of a started transfer; 2.1.0 adds that endpoint but answers a catalog request against a
TMForum-backed provider with `Querying for contract definitions is currently not supported`, which
2.1.1 fixes. The fdsc-edc chart (`0.7.10`) still carries appVersion 1.8.7 and no chart with a 2.x
appVersion is published yet, so the umbrella sets `fdsc-edc.common.deployment.image.tag: "2.1.1"`.
It applies to every fdsc-edc deployment, `oid4vc` included, and goes away with the next fdsc-edc
chart bump. A deployment that sets its own `deployment.image.tag` overrides the pin and keeps
whatever image it names.

### Breaking changes

All of them concern the DCP controlplane only.

- **Participant contexts.** The DID and the STS client move from the global configuration into
  `fdsc.participants.<key>.*`. The DSC uses the participant DID as context id, which reuses the
  IdentityHub participant, its STS client and the vault alias `<did>-sts-client-secret` the
  bootstrap Job already writes.
- **DSP paths.** DSP requests go to `<protocol path>/<context id>/<profile>/...` and the version
  metadata to `<protocol path>/<context id>/.well-known/dspace-version`. The callback address
  must contain `%s`, which the connector replaces by the context id.
- **Management API.** v3 and v4 are removed. Calls go to
  `<management path>/v5beta/participants/<context id>/...` and need an OAuth2 JWT with the scopes
  `management-api:read` / `management-api:write`. `management-api:admin` grants every context;
  without it, the token's `sub` must equal the context id. In request bodies `protocol` names a
  profile, e.g. `http-dsp-profile-2025-1`.
- **Stricter policy validation.** A contract request is refused with
  `400 object found, array expected` when `policy.permission[].constraint` holds a bare object. It
  has to be a list, which is the shape the catalog returns, so a consumer that repeats the offer
  from the catalog verbatim is unaffected. v3 accepted both, so hand-written request bodies that
  worked before need the constraint wrapped.
- **TMForum.** `tmfExtension.defaultParticipantContextId` names the context that owns existing,
  untagged TMForum data, and `tmfExtension.schemaBaseUri` points to schemas that carry the new
  `participantContextId(s)` properties.
- **Globally unique ids.** Resolving a policy id held by more than one product offering now fails
  with `Policy <id> is used by multiple offerings`. The same applies to offering `externalId`s.
- **Removed:** `testExtension.*` has no effect on the DCP image any more, and the root DSP version
  endpoint is gone.

### :warning: Required action: DCP deployments

The fdsc-edc chart has no dedicated value for any of the new keys. They all go into
`fdsc-edc.deployment.dcp.config.additionalProperties`, a string rendered without indentation, so
every continuation line carries exactly 4 leading spaces. A per-deployment `additionalProperties`
replaces the one in `fdsc-edc.common`, so repeat the common entries (the
`edc.http.client.timeout.*` lines). [`k3s/dsp-provider.yaml`](../../k3s/dsp-provider.yaml) is a
complete example.

- [ ] Declare one participant context per DID: `fdsc.participants.<key>.id` and `.identity` set to
      the DID, `.profiles` set to `http-dsp-profile-2025-1` (or the profiles you declare under
      `edc.dataspace.profiles.*`), and the three `.config.edc.iam.sts.oauth.*` keys with the
      values of `config.oauth`.
- [ ] Add `%s` to the callback: `config.edc.dspCallback: https://<host>/api/dsp/%s`.
- [ ] Set `tmfExtension.defaultParticipantContextId=<DID>` and `tmfExtension.schemaBaseUri` to a
      copy of the fdsc-edc `schemas/` the TMForum API can reach, with a trailing `/`, e.g.
      `https://raw.githubusercontent.com/SEAMWARE/fdsc-edc/2.1.1/schemas/`.
- [ ] Set `edc.iam.oauth2.issuer` (the `iss` your identity provider puts in tokens) and
      `edc.iam.oauth2.jwks.url`, and create a client-credentials client whose tokens carry the
      `management-api:*` scopes. Move every management client to the v5beta paths.
- [ ] Hand counterparties the new DSP address `https://<host>/api/dsp/<DID>/<profile>`, and move
      PEP exemptions for `/.well-known/dspace-version` to `/api/dsp/<DID>/.well-known/dspace-version`.
- [ ] Wrap `policy.permission[].constraint` in a list in every hand-written contract request, or
      build the policy from the catalog offer.
- [ ] Drop `testExtension.*` from the DCP deployment's values.
- [ ] Check the TMForum catalog for duplicate policy ids and offering `externalId`s before
      upgrading.

## 11.0.0 — identityhub bootstrap works with a full super-user token

`identityhub.bootstrap` and `identityhub.credentialSync` built the Identity API token as
`base64(superUserId).<identityhub.superuser.key>`, while `identityhub-deployment.yaml` passes that
same value verbatim to the identityhub as `EDC_IH_API_SUPERUSER_KEY`, where it is the whole token
(`c3VwZXItdXNlcg==.random`). A deployment that set it in that form - the form the identityhub
itself needs - had every bootstrap and credential-sync call rejected with
`401 Invalid API token`. `superuser_token()` now passes the key through unchanged when it already
carries the `base64(superUserId).` prefix, and still prefixes the bare secret that
[DSP integration](../DSP_INTEGRATION.md) exports as `API_KEY`. No action is required; a deployment
whose bootstrap Job failed this way completes on the next upgrade.

The local `dsp` scenario now enables both switches
([`k3s/dsp-provider.yaml`](../../k3s/dsp-provider.yaml),
[`k3s/dsp-consumer.yaml`](../../k3s/dsp-consumer.yaml)), so `mvn clean deploy -Plocal,dsp` brings up
two connectors with registered participants and their membership credentials, see the
[demo flows](../MULTI_DATASPACE.md#demo-flows).

## 11.0.0 — consent management moves to dsc-consent-manager

The consent-manager of the consent management scenario is replaced: the Prometheus-X service
(Node, MongoDB, a shared consent key, APISIX facade routes at the authority) gives way to
[dsc-consent-manager](https://github.com/SEAMWARE/dsc-consent-manager) (Java, PostgreSQL), which
validates the JWT of the authority's VCVerifier on every call. See
[ADR 0008](../adr/0008-dsc-consent-manager.md) and
[Consent Management](../CONSENT_MANAGEMENT.md), which also describes the
[migration](../CONSENT_MANAGEMENT.md#migrating-from-the-prometheus-x-consent-manager).

**The data-space-connector chart only loses one value:** `consentManagement.enabled`, which no
template ever read. The provider side is the `consent-facade` and `consent-owner-resolver`
subcharts plus the consent-plugin on the provider's APISIX, each with its own `enabled`. Drop the
key from your values - `values.schema.json` rejects what the chart does not declare. A provider that
does not use consent management has nothing to do.

The breaking changes for consent users are elsewhere:

- **trust-anchor chart 2.0.0** deploys `dsc-consent-manager` 0.1.0 under the unchanged
  `consent-manager` key, pinned to image **0.0.3** with
  `consent-manager.deployment.image.tag` because that chart's `appVersion` is still 0.0.1. The
  pin is required, not cosmetic. Before 0.0.3:
  - 0.0.1 answers every `POST /v1/privacy-notices/by-contract` with a 502 against a contract
    service that keeps only bilateral contracts - which the consent-facade is, since it answers
    the ecosystem endpoint with 501;
  - it cannot be exempted from a global HTTP proxy at all, because a client set to
    `proxy-type: DIRECT` inherits the global proxy address and then fails every request;
  - a contract party was identified by the participant identifier alone, while the
    consent-facade's `/verify` - the lookup the owner-resolver makes to find the governing
    contract - matches only the participants' self-description URLs. One agreement can carry
    only one form in `provider-id`/`consumer-id`, so notice generation and the consent gate
    could not both work: with DIDs every gated read was denied, with URLs generation answered
    `404 No active participant is registered under '<url>'`. 0.0.3 accepts either name
    (ADR-0017 of dsc-consent-manager), and the agreements this deployment writes carry the
    self-description URLs, as `contract-management` already did.

  Drop the pin once the dependency moves to a chart whose `appVersion` is 0.0.3 or newer.
  - The consent MongoDB and its values are gone. The service stores its data in the chart's
    Zalando `managedPostgres`, under a user and database both fixed to `consent_manager`. External
    Postgres is not supported.
  - The consent key is gone. Callers authenticate with a JWT of the VCVerifier service
    `consent-manager`, set with `consent-manager.identityProviders.primary`.
  - A setup Job (`consentManagement.setup`) copies the database credentials into
    `consent-manager-env` and generates the receipt signing key in `consent-manager-signing-keys`,
    once; it never rotates them. The database itself is created by the Zalando operator from
    `managedPostgres.config.databases`, on a fresh cluster and on an existing volume alike.
    `consentManagement.setup.resources` sizes its containers, and its ServiceAccount and RBAC can be
    managed outside the chart with `consentManagement.setup.serviceAccount.create` / `.name` and
    `consentManagement.setup.rbac.create`.
  - SMTP credentials come from `consentManagement.smtp.existingSecret`.
  - The consent-manager's NetworkPolicy admits its management port (9090) to
    `consentManagement.networkPolicy.metricsScrapers` only. Enabling
    `consent-manager.serviceMonitor` without listing the scraping Prometheus there drops every
    scrape.
  - The chart `fail`s on the removed values: `managedMongo`, `consentManagement.mongo`,
    `consent-manager.mongo`, `consent-manager.secret.consentKey`, `consent-manager.externalIdp`,
    `consent-manager.appEndpoint`, `consent-manager.contractService` and
    `consent-manager.secrets.smtpUser`/`smtpPassword`.
- **The provider's consent route needs consent-filter plugin 1.0.0**, which speaks only the `/v1`
  API, so the image and the route config change together. `consent_api_url` points at the
  consent-manager directly; there is no authority facade in between. `consent_api_host` and
  `consent_key` are removed. `check_mode`, `consumer_claim`, `require_purpose` and
  `require_contract` are new. Provider and consumer must both be registered participants at
  the consent-manager.

Consents stored in MongoDB are not migrated. Data subjects have to grant them again under the new
service.
