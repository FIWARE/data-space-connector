# Release 11.x.x

Version 11.x.x of the Data Space Connector replaces the consent-manager of the consent management
scenario and adds data space eventing. Changes will be listed below, together with the required
actions for migration.

The breaking change is 11.0.0 and only deployments that use consent management are affected: the
data-space-connector chart loses one value that no template read, while the breaking changes are in
the trust-anchor chart and in the consent-filter plugin. Data space eventing (11.1.0) is additive
and off by default.

## 11.1.0 — Data space eventing

contract-management (CM) can now take part in data space eventing as a participant: it subscribes at
the data space's publisher, receives its events on `POST /events` and reacts to the removal of a
participant. The feature is **off by default**; the operator guide is
[`doc/eventing/participant-setup.md`](../eventing/participant-setup.md). With default values no
eventing ConfigMap, route, env entry or volume appears, and the registration Job's script is
unchanged. The feature needs two component upgrades, which a default upgrade does bring along; they
are listed below.

### Component upgrades

| Chart | Version | Image |
|---|---|---|
| `contract-management` | 3.6.3 → 3.6.7 | 3.4.2 → 3.5.4 |
| `decentralized-iam` | 2.1.28 → 2.3.0 | see below |

CM 3.5.4 is the first release that sends the scope type as `dataspace-membership`; 3.5.3 sent
`DATASPACE_MEMBERSHIP`, which the TIL refuses, so it could neither report `held` grants nor reconcile
or use the writing modes.

`decentralized-iam` 2.3.0 moves odrl-authorization 2.4.3 → 2.5.0, the apisix chart 2.16.0 → 2.18.2
and vc-authentication 1.5.2 → 1.6.0. What a default upgrade changes:

- **Images:** APISIX `3.17.0-ubuntu` → `3.19.0-ubuntu` (no `wait-etcd` init container any more),
  trusted-issuers-list (TIL) `0.10.0` → `0.10.3` (chart 0.19.1 → 0.19.2), VCVerifier `6.27.0` →
  `6.31.0`, odrl-pap `1.7.1` → `1.8.1`.
- **TIL database migration:** TIL 0.10.1 adds the nullable column `scope_type` to the `credential`
  table at start-up (Liquibase). Existing grants stay unscoped. There is no rollback changeset: after a
  rollback to 0.10.0 the column stays, and grants written with a `scopeType` lose it.
- **The APISIX etcd is removed.** The default APISIX mode (standalone, routes from a ConfigMap) never
  used it, so the umbrella now sets `decentralizedIam.odrlAuthorization.apisix.etcd.enabled: false`.
  The StatefulSet `<release>-etcd` and its Services, PDB, NetworkPolicy, ServiceAccount, Secret and
  pre-upgrade Job are deleted. Its PVCs `data-<release>-etcd-*` are not deleted by Helm; remove them
  by hand.
- **etcd-backed APISIX modes must enable etcd.** odrl-authorization 2.5.0 fails the render of a
  `traditional` + etcd mode without an etcd. Deployments that use it set
  `decentralizedIam.odrlAuthorization.apisix.etcd.enabled: true` (or `apisix.externalEtcd.host`), as
  the k3s files do.
- **Gateway Service type:** odrl-authorization 2.5.0 defaults the APISIX gateway Service to
  `ClusterIP`; the umbrella pins `decentralizedIam.odrlAuthorization.apisix.service.type: NodePort`,
  so the node port stays open. Set `ClusterIP` when the gateway is only reached through an Ingress.
- **The default catch-all route is gone:** odrl-authorization's `catchAllRoute.enabled` now defaults
  to `false`, so the example `/*` → `http://my-broker:8080` route disappears from `apisix-routes`.
- **New Service `<release>-apisix-control`** (ClusterIP, port 9090) and a Secret
  `etcd-<release>-apisix` with an empty password. APISIX binds its control API to `127.0.0.1`, so the
  Service reaches nothing.
- `helm.sh/chart` and `app.kubernetes.io/version` labels change on the CM and decentralized-iam
  resources.

### :warning: CM's management port 9090 must stay cluster-internal

CM ≥ 3.5.3 answers an unauthenticated `POST :9090/refresh` (re-reads its configuration) in **every**
deployment with CM enabled, not only with eventing on; in 3.4.2 it answered `401`. The CM Service only
exposes 8080, so the port is reachable by pod IP inside the cluster only. Keep it that way: no
Service, Ingress or route for 9090, and a NetworkPolicy where pod IPs are reachable. With eventing on,
9090 also serves `GET /participants-removed`.

To restore the old behaviour, add `ENDPOINTS_REFRESH_SENSITIVE=true` to
`contract-management.additionalEnvVars`. That value is a list and Helm replaces lists, so copy the
**whole** default list (the `OTEL_*` entries in the chart's `values.yaml`) into your values and add
the entry to it; setting only the new entry drops the tracing variables.

### New values

- `contract-management.dataspace.events`: CM's `dataspace.events` configuration, passed verbatim
  (kebab-case keys). With `listener.enabled` or `subscriber.enabled` the CM chart renders it into the
  ConfigMap `contract-management-dataspace-events`, mounted as a directory and watched, so a change to
  `publishers` reaches the running pod; a change to a startup-only key rolls it.
- `registration.issuer[].scope` and `scopeType`: the trusted issuers the registration Job writes are
  granted with `scope` = the id of the publisher of `org.fiware.dataspace.participant.removed`
  (from `contract-management.dataspace.events.publishers`) and `scopeType` = `dataspace-membership`,
  so CM's `on-participant-removed.mode: dataspace` can revoke them. Without such a publisher nothing
  changes; `scope: ""` keeps an issuer unscoped. An issuer that is already registered keeps its
  unscoped grant (`409`); CM's `on-participant-removed.adopt-unattributed` covers it.
- **A TIL outside the release** (`registration.til`) must be ≥ 0.10.3, the version the chart ships.
  Each part needs: 0.10.1 for the scoped grant (an older one accepts the scoped request and silently
  stores an unscoped grant); 0.10.2 for the `dataspace`, `granted` and `full` reactions, without
  which CM fails to start, and for a complete `report`, which otherwise runs degraded (health
  `DEGRADED`, removals reported without what the participant holds); 0.10.3 for
  `adopt-unattributed`, without which CM fails to start.
- `eventingRouteValidation.enabled` (default `true`): see below.

### Gateway routes and their validation

The chart ships no events route. Operators append the three entries of
[`doc/eventing/examples/events-routes.yaml`](../eventing/examples/events-routes.yaml)
(`dataspace-events`, `dataspace-events-handshake`, `dataspace-events-discovery`) to their own
`decentralizedIam.odrlAuthorization.apisix.routes` list. The new template
`templates/eventing-validation.yaml` finds them by `name` and fails install and upgrade on settings
that weaken access control (no token check, no ODRL policy, a client-sent `X-Userinfo` reaching CM,
an unbound host, the APISIX ingress-controller mode, ...). The guide lists every check;
[ADR 0009](../adr/0009-events-routes-as-validated-operator-snippet.md) records why the routes are a
snippet and not part of the chart. `eventingRouteValidation.enabled: false` switches every check off;
the operator then owns the route security.

### :warning: Possible upgrade failure: routes with the events names

The validation is on by default. It only looks at routes named `dataspace-events`,
`dataspace-events-handshake` or `dataspace-events-discovery`, so an upgrade without such routes cannot
fail. An existing route that happens to carry one of those names and does not pass the checks fails
`helm upgrade`. Rename it, or set `eventingRouteValidation.enabled: false`.

### Trust anchor side, demo and integration test

- **The publisher.** The data space's publisher is a contract-management in publisher and TIR-watcher
  mode, run as the `contract-management` of the authority's own DSC release. It reuses that release's
  identity, OperatorCredential, verifier and APISIX; the `trust-anchor` chart is unchanged. The guide is
  [`doc/eventing/trust-anchor-setup.md`](../eventing/trust-anchor-setup.md).
- **contract-management pitfalls.** A publisher-only CM needs the env var `NOTIFICATION_ENABLED=false`:
  the CM chart's `notification.enabled: false` omits the block, CM defaults to `true` and its health
  goes `DOWN` without TM Forum. `contract-management.additionalEnvVars` is a list, so copy the default
  `OTEL_*` entries into it. A subscriber needs `dataspace.events.subscriber.protocol-settings.client-id`;
  CM does not start without it.
- **No trust change by default.** With eventing on and the default removal mode `report`, a removal is
  only recorded in `GET :9090/participants-removed`; no grant is written or deleted. The integration
  test's first scenario checks exactly that.
- **Demo and test.** `mvn clean deploy -Plocal,eventing` deploys the publisher in the `consent-authority`
  release and wires provider and consumer to it
  ([`k3s/eventing-trust-anchor.yaml`](../../k3s/eventing-trust-anchor.yaml) and the `eventing-provider`/`eventing-consumer` overlays next to it);
  [`doc/scripts/dataspace-eventing-demo.sh`](../scripts/dataspace-eventing-demo.sh) removes, restores and
  reports. The `@eventing` feature runs in CI as `-Ptest,eventing,eventing-test`, with and without
  `helm-install`. See [`doc/EVENTING.md`](../EVENTING.md).

## 11.0.0 — consent management moves to dsc-consent-manager

The consent-manager of the consent management scenario is replaced: the Prometheus-X service
(Node, MongoDB, a shared consent key, APISIX facade routes at the authority) gives way to
[dsc-consent-manager](https://github.com/SEAMWARE/dsc-consent-manager) (Java, PostgreSQL), which
validates the JWT of the authority's VCVerifier on every call. See
[ADR 0008](../adr/0008-dsc-consent-manager.md) and
[Consent Management](../CONSENT_MANAGEMENT.md), which also describes the
[migration](../CONSENT_MANAGEMENT.md#migrating-from-the-prometheus-x-consent-manager).

**The data-space-connector chart only loses one value:** `consentManagement.enabled`, which no
template ever read. The provider side is the `consent-facade` and `consent-owner-resolver`
subcharts plus the consent-plugin on the provider's APISIX, each with its own `enabled`. Drop the
key from your values - `values.schema.json` rejects what the chart does not declare. A provider that
does not use consent management has nothing to do.

The breaking changes for consent users are elsewhere:

- **trust-anchor chart 2.0.0** deploys `dsc-consent-manager` 0.1.0 under the unchanged
  `consent-manager` key, pinned to image **0.0.3** with
  `consent-manager.deployment.image.tag` because that chart's `appVersion` is still 0.0.1. The
  pin is required, not cosmetic. Before 0.0.3:
  - 0.0.1 answers every `POST /v1/privacy-notices/by-contract` with a 502 against a contract
    service that keeps only bilateral contracts - which the consent-facade is, since it answers
    the ecosystem endpoint with 501;
  - it cannot be exempted from a global HTTP proxy at all, because a client set to
    `proxy-type: DIRECT` inherits the global proxy address and then fails every request;
  - a contract party was identified by the participant identifier alone, while the
    consent-facade's `/verify` - the lookup the owner-resolver makes to find the governing
    contract - matches only the participants' self-description URLs. One agreement can carry
    only one form in `provider-id`/`consumer-id`, so notice generation and the consent gate
    could not both work: with DIDs every gated read was denied, with URLs generation answered
    `404 No active participant is registered under '<url>'`. 0.0.3 accepts either name
    (ADR-0017 of dsc-consent-manager), and the agreements this deployment writes carry the
    self-description URLs, as `contract-management` already did.

  Drop the pin once the dependency moves to a chart whose `appVersion` is 0.0.3 or newer.
  - The consent MongoDB and its values are gone. The service stores its data in the chart's
    Zalando `managedPostgres`, under a user and database both fixed to `consent_manager`. External
    Postgres is not supported.
  - The consent key is gone. Callers authenticate with a JWT of the VCVerifier service
    `consent-manager`, set with `consent-manager.identityProviders.primary`.
  - A setup Job (`consentManagement.setup`) copies the database credentials into
    `consent-manager-env` and generates the receipt signing key in `consent-manager-signing-keys`,
    once; it never rotates them. The database itself is created by the Zalando operator from
    `managedPostgres.config.databases`, on a fresh cluster and on an existing volume alike.
    `consentManagement.setup.resources` sizes its containers, and its ServiceAccount and RBAC can be
    managed outside the chart with `consentManagement.setup.serviceAccount.create` / `.name` and
    `consentManagement.setup.rbac.create`.
  - SMTP credentials come from `consentManagement.smtp.existingSecret`.
  - The consent-manager's NetworkPolicy admits its management port (9090) to
    `consentManagement.networkPolicy.metricsScrapers` only. Enabling
    `consent-manager.serviceMonitor` without listing the scraping Prometheus there drops every
    scrape.
  - The chart `fail`s on the removed values: `managedMongo`, `consentManagement.mongo`,
    `consent-manager.mongo`, `consent-manager.secret.consentKey`, `consent-manager.externalIdp`,
    `consent-manager.appEndpoint`, `consent-manager.contractService` and
    `consent-manager.secrets.smtpUser`/`smtpPassword`.
- **The provider's consent route needs consent-filter plugin 1.0.0**, which speaks only the `/v1`
  API, so the image and the route config change together. `consent_api_url` points at the
  consent-manager directly; there is no authority facade in between. `consent_api_host` and
  `consent_key` are removed. `check_mode`, `consumer_claim`, `require_purpose` and
  `require_contract` are new. Provider and consumer must both be registered participants at
  the consent-manager.

Consents stored in MongoDB are not migrated. Data subjects have to grant them again under the new
service.
