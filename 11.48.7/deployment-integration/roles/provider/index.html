    Provider Role¶

    Overview¶

    A Provider is an organization that offers data services to other participants in the data space (e.g. APIs, data services web applications, etc). The provider hosts one or more services and protects them with a full decentralized identity and access management stack. Incoming requests must present valid Verifiable Credentials, which are verified against the data space's trust framework and evaluated against ODRL access policies.

    These services can be: - APIs — RESTful APIs, NGSI-LD endpoints or any other HTTP-based service - Web applications — applications that integrate with Verifiable Credentials via OID4VC for user authentication and authorization

    A provider may also needs the ability to issue its own Verifiable Credentials (for its employees or services), so it includes all the components of a Consumer plus additional authentication, authorization, and data service components.

    Before you start¶

    Before deploying, contact the Data Space Operator to initiate the onboarding process for your organization. The Operator will guide you through:

    • The documentation and requirements needed to join the data space
    • Registration of your organization's DID at the Trust Anchor
    • The credential types your organization is allowed to issue and their required configuration (claims, attribute mappings, etc.)
    • The Trust Anchor's TIR endpoint URL

    This information is essential for configuring Keycloak, the DID, the VCVerifier, and the Verifiable Credentials correctly.

    Check also that the cluster meets the Cluster Prerequisites: its databases, the network requirements and the resources the provider needs.

    Required components¶

    Note

    The data services that the provider wants to expose through the FIWARE Data Space Connector (APIs, web applications, etc.) are not included in this list. These are external to the connector and must be deployed and managed independently.

    Everything from the Consumer role¶

    The provider needs the same base components as a consumer: - Keycloak — VC issuer for the provider's own users. For detailed configuration instructions, see the Keycloak Configuration guide. - DID Helper — publishes the provider's DID document - PostgreSQL — database for Keycloak and the IAM components: an existing one, or one the chart deploys (see Databases)

    Note

    If the data space uses the Decentralized Claims Protocol (DCP) (typically together with the Dataspace Protocol via FDSC-EDC), the DID Helper is replaced by the Identity Hub, which serves the DID document (and the provider's credentials) as required by DCP. See the Dataspace Protocol Integration Guide for details.

    Authentication: Verifiable Credential verification¶

    Component Description
    VCVerifier Verifies incoming Verifiable Credentials via OID4VP. Checks credential signatures, issuer trust (via the Trust Anchor), and credential type acceptance. Returns a JWT access token on success.
    Credentials configuration Which credential types are accepted for each protected service, and which Trusted Issuers Lists and Trusted Participants Lists to check. Served by the VCVerifier itself, on its configuration API (port 8090); the services are registered there from the values with vcverifier.registration.services. The standalone Credentials Config Service is no longer needed and is disabled by default.
    Trusted Issuers List (local) The provider's own list of trusted issuers, used in combination with the Trust Anchor's registry to determine which organizations can issue specific credential types.

    Authorization: Policy enforcement¶

    Component Description
    APISIX API Gateway that acts as the Policy Enforcement Point (PEP). Validates JWT tokens from VCVerifier and delegates authorization decisions to OPA. All external access to protected services goes through APISIX.
    OPA (Open Policy Agent) Policy Decision Point (PDP). Evaluates authorization policies (in Rego format, generated from ODRL) for each incoming request and returns allow/deny decisions.
    ODRL-PAP Policy Administration Point. Allows the provider to define access policies using ODRL (Open Digital Rights Language). Translates ODRL policies into Rego for OPA.

    Databases¶

    Keycloak, the Trusted Issuers List, the VCVerifier, the ODRL-PAP and Scorpio store their data in PostgreSQL; the local marketplace also needs MongoDB (see Running a local marketplace). Use databases you already run, or let the chart deploy them:

    • A PostgreSQL deployed by the chart (decentralizedIam.vcAuthentication.managedPostgres, the default): a single cluster named postgres in the connector's namespace, with a database for each component, created by the Zalando Postgres Operator. The chart installs that operator by default too (decentralizedIam.vcAuthentication.postgres-operator.enabled); if one already runs in the cluster - for example installed by another connector or by the Trust Anchor - disable it in this release, since the operator's cluster-wide resources can only belong to one release.
    • An existing PostgreSQL: disable both, create a database and a user for each component, store the passwords in Secrets of the connector's namespace, and point each component to them:
    decentralizedIam:
  vcAuthentication:
    managedPostgres:
      enabled: false
    postgres-operator:
      enabled: false
    trusted-issuers-list:
      database:
        host: <your_postgres_host>
        port: 5432
        name: <til_database>
        username: <til_user>
        existingSecret:
          enabled: true
          name: <til_secret>
          key: password
    vcverifier:
      deployment:
        database:
          host: <your_postgres_host>
          name: <verifier_database>
          existingSecret:
            name: <verifier_secret>               # holds both the user and the password
            usernameKey: username
            passwordKey: password
  odrlAuthorization:
    odrl-pap:
      database:
        url: jdbc:postgresql://<your_postgres_host>:5432/<pap_database>
        username: <pap_user>
        existingSecret:
          enabled: true
          name: <pap_secret>
          key: password
keycloak:
  database:
    host: <your_postgres_host>
    name: <keycloak_database>
    existingSecret: <keycloak_secret>             # holds both the user and the password
    secretKeys:
      usernameKey: username
      passwordKey: password
scorpio:
  db:
    dbhost: <your_postgres_host>
    user: <scorpio_user>
    existingSecret:
      enabled: true
      name: <scorpio_secret>
      key: password

    Scorpio needs the PostGIS extension in its database; the examples in k3s/ create it, as a database named ngb, through the operator's preparedDatabases. The Identity Hub and the status list server, when enabled, take their database settings under identityhub.postgresql and statusListServer.postgresql.

    The Trusted Issuers List and the Credentials Config Service apply their database migrations at startup - on the first start, and after an upgrade that brings new ones - holding a lock in the databasechangeloglock table of their database while they do. If the pod is killed in the middle of the migrations (out of memory, a failed node, a pod deleted during an upgrade), the lock stays set, and the next start logs Waiting for changelog lock.... and never completes. Release the lock in that database: the waiting pod then takes it and applies the remaining migrations. Do it only while no other pod of the service is applying them. With the chart's PostgreSQL, whose databases are tildb and ccsdb:

    kubectl exec -n <namespace> postgres-0 -- psql -U postgres -d tildb \
  -c 'UPDATE databasechangeloglock SET locked = false, lockgranted = NULL, lockedby = NULL WHERE id = 1;'

    Optional components¶

    All optional components listed below can be deployed using the fiware/data-space-connector Helm chart. Some of them - Scorpio, the TMForum API and Contract Management - are enabled by default; set them to false explicitly if you do not need them. The values example below lists the default of each one.

    Note on Scorpio Context Broker

    The FIWARE implementation of the TMForum APIs is based on NGSI-LD, which is why the fiware/data-space-connector Helm chart deploys a Scorpio Context Broker as its backend. In the provided examples, this same Scorpio instance is also used as the NGSI-LD endpoint that the provider exposes through the connector. However, in production, if you want to expose an NGSI-LD endpoint as a data service, you should deploy a separate Context Broker for that purpose and not reuse the Scorpio instance that backs the TMForum APIs.

    TMForum API¶

    The TMForum API implements standardized APIs for product catalog management, ordering, inventory, and more. These APIs are used both by the provider's own local marketplace and by the central marketplace if one exists in the data space. Enable this when: - You want to offer data products through a structured catalog - You need standardized product ordering workflows - You plan to use contract-based access control - You want to publish offerings to a central marketplace

    Contract Management¶

    The Contract Management component automates access control based on product orders. When a consumer purchases a product offering via the TMForum API, Contract Management reacts to the order and registers the consumer's DID in the provider's local Trusted Issuers List, so the consumer's credentials are accepted at the provider when accessing the purchased service. The credential types granted to the consumer are taken from the ordered product. Additionally, if the ODRL-PAP is deployed, Contract Management also creates the ODRL access policies that encode the contract terms. Enable this when: - You use TMForum APIs for product ordering - Access should be granted/revoked automatically based on contracts - You need audit trails for data access agreements

    Note

    If the data space uses a central marketplace, the Contract Management component requires specific configuration to work with it. See the Central Marketplace documentation for details on how to configure Contract Management in that scenario.

    Note

    The policies and the credential configuration are read from the ordered ProductSpecification by default. A product can instead be composed of ServiceSpecifications that carry their own policies - an access policy protects an API, and in TMForum an API is a ServiceSpecification. See Authoring a composed ProductSpecification.

    Marketplace (BAE)¶

    A provider can offer its products and services through a marketplace in two ways:

    • Local marketplace — Deploy a marketplace as part of the provider's own connector. The Business API Ecosystem provides a web portal for browsing and ordering product offerings directly from this provider. See Running a local marketplace.
    • Central marketplace — If the data space operates a shared central marketplace, the provider can publish its offerings there instead of (or in addition to) running its own. See the Central Marketplace documentation for details.

    Enable the local marketplace when: - You want a user-facing web interface for your own data marketplace - Consumers should be able to browse and order offerings through a portal hosted by the provider

    Note

    The local Marketplace requires MongoDB in addition to the existing PostgreSQL, deployed by the chart through the MongoDB Community Operator. Running a local marketplace covers the whole setup: the operator, the values, the login with Verifiable Credentials and the security considerations.

    Note

    To create DSP-compatible products and offerings (i.e. offerings whose data is exchanged over the Dataspace Protocol — see FDSC-EDC (Dataspace Protocol)) through the local marketplace UI, the BAE Logic Proxy must be deployed with BAE_LP_DSP_ENABLED=true, set under marketplace.bizEcosystemLogicProxy.additionalEnvVars. This flag exposes the DSP-specific fields in the offering-creation forms; omit it for a marketplace that only brokers classic FIWARE offerings. See Using the BAE Marketplace in the DSP Integration documentation.

    Participating in a Central Marketplace¶

    If the data space runs a shared Central Marketplace hosted by another actor (typically the Data Space Operator), the provider publishes its offerings there and does not deploy the marketplace itself. However, the provider's DSC needs specific configuration so the Central Marketplace can reach the local Contract Management and trigger the activation flow after each purchase.

    Minimum versions

    • fiware/data-space-connector Helm chart ≥ 9.0.1
    • fiware/contract-management Helm chart ≥ 3.5.22
    • contract-management container image ≥ 3.3.8

    The following configuration is required on the provider side. The example in k3s/provider.yaml already includes all of the pieces below and can be used as a reference.

    1. Enable and configure Contract Management in central-marketplace mode

    contract-management:
  enabled: true
  enableCentralMarketplace: true          # react to order notifications coming from an external marketplace
  enableOdrlPap: true                     # write ODRL policies to the local PAP on contract activation
  did: <your-organization-DID>
  til:
    credentialType: <YourCredentialType>  # e.g. OperatorCredential — registered in the local TIL on activation
  services:
    odrl:
      url: http://odrl-pap:8080
    # ... TMForum URLs, trusted-issuers-list, etc.
  notification:
    enabled: true
    host: contract-management
  deployment:
    image:
      tag: 3.3.8                          # minimum image required for central marketplace mode
    • enableCentralMarketplace activates the flow that reacts to order notifications coming from an external marketplace (instead of reacting to local orders only).
    • enableOdrlPap: true is required so that the ODRL policies attached to each purchased offering are installed in the provider's PAP when the contract is activated.
    • til.credentialType defines the credential type that Contract Management will register for each buyer in the local Trusted Issuers List when a purchase is completed.

    2. Expose Contract Management externally through APISIX

    The Central Marketplace sends order notifications to the provider's Contract Management over HTTPS, authenticating with its MarketplaceCredential. APISIX must expose the Contract Management on a dedicated host with the standard OIDC + OPA protection:

    decentralizedIam:
  odrlAuthorization:
    apisix:
      ingress:
        hosts:
          - host: <your_contract_management_domain>    # e.g. provider-cm.example.org
            paths: ["/"]
      routes:
        # Well-known endpoint for Contract Management — proxied to the verifier
        - uri: /*/.well-known/openid-configuration
          host: <your_contract_management_domain>
          upstream:
            nodes:
              verifier:3000: 1
            type: roundrobin
          plugins:
            proxy-rewrite:
              uri: /services/contract-management/.well-known/openid-configuration
        # Catch-all route to Contract Management, protected by VCVerifier + OPA
        - uri: /*
          host: <your_contract_management_domain>
          upstream:
            nodes:
              contract-management:8080: 1
            type: roundrobin
          plugins:
            openid-connect:
              bearer_only: true
              use_jwks: true
              client_id: contract-management
              client_secret: unused
              ssl_verify: true            # see "Trusting a private CA" below if your certificates are not publicly trusted
              discovery: http://verifier:3000/services/contract-management/.well-known/openid-configuration
            opa:
              host: http://localhost:8181
              policy: policy/main
              with_body: true

    3. Register the Contract Management as a service at the VCVerifier

    The VCVerifier needs to know which credential types to accept on the Contract Management host. Register the service with a dedicated OIDC scope (external-marketplace) that accepts the MarketplaceCredential:

    decentralizedIam:
  vcAuthentication:
    vcverifier:
      registration:
        enabled: true
        services:
          - id: contract-management
            defaultOidcScope: "external-marketplace"
            authorizationType: "DEEPLINK"
            oidcScopes:
              "external-marketplace":
                credentials:
                  - type: MarketplaceCredential
                    trustedParticipantsLists:
                      - <trust_anchor_tir_url>     # Trust Anchor's TIR endpoint
                    trustedIssuersLists:
                      - "*"                        # any issuer registered at the Trust Anchor
                    jwtInclusion:
                      enabled: true
                      fullInclusion: true

    Add the entry to the same registration.services list as the provider's other services (such as the data-service of the values example): Helm replaces lists instead of merging them, so a list in a second values file drops the first one.

    trustedIssuersLists: "*" is intentional here: the marketplace's credential is issued by the marketplace itself, and the trust decision is delegated entirely to the Trust Anchor's TIR.

    4. Register the allowContractManagement policy at the PAP

    Before receiving the first notification, the provider must install a policy at its PAP granting the Central Marketplace access to the Contract Management endpoint. See Prepare the provider (Step 1) in the Central Marketplace documentation for the exact policy and the curl command.

    5. Register the provider as an Organization at the Central Marketplace

    The Central Marketplace needs to know the provider's Contract Management endpoint and the OIDC client to authenticate with. This registration can be done through the TMForum API (partyCharacteristic.contractManagement) or through the Marketplace UI (Profile form). See Prepare the provider (Step 1) and Using the Marketplace UI in the Central Marketplace documentation for both variants.

    Enable the Eclipse Dataspace Components connector for DSP compliance. See DSP Integration.

    Deployment¶

    Using the FIWARE DSC Helm chart and values¶

    Start from the reference profile

    examples/provider.yaml, and examples/provider-marketplace.yaml for the provider's own local marketplace (not the Central Marketplace), are complete values files for a provider, to adapt to your installation. Their README lists the prerequisites, the placeholders, the Secrets to create and the installation steps. The settings below explain each part.

    The provider uses the fiware/data-space-connector chart with authentication and authorization components enabled.

    Build a values.yaml for the provider by adapting examples/provider.yaml. The sections below show that file piece by piece and explain the key settings; replace every <placeholder>.

    The ingresses use cert-manager through annotations and the ingress class you set, so adapt them to the controller your cluster runs (the local deployment uses Traefik). A ClusterIssuer is a prerequisite: use your own, or let the chart create one with certManagerResources (the examples README covers the prerequisites, Secrets and placeholders).

    Identity: did:web¶

    did-helper serves the organization's did:web. Its key is the TLS certificate cert-manager issues for the ingress, and it must never rotate: a new key changes the DID, and every credential issued with the old one stops verifying (hence private-key-rotation-policy: Never; see Identity key lifecycle). did-helper also publishes that certificate at /.well-known/tls.crt, as the x5u of the key.

    did:
  enabled: true
  config:
    server:
      # did-helper also publishes <hostUrl>/.well-known/tls.crt, the certificate of the key
      hostUrl: https://<did-domain>
      certPath: /certs/tls.crt
  volumes:
    - name: certs
      secret:
        # the DID's key: the certificate cert-manager issues for the ingress below
        secretName: did-tls
        items:
          - key: tls.crt
            path: tls.crt
  volumeMounts:
    - name: certs
      mountPath: /certs
  # with certPath did-helper writes nothing, so it runs on a read-only root filesystem
  securityContext:
    readOnlyRootFilesystem: true
    allowPrivilegeEscalation: false
    capabilities:
      drop: ["ALL"]
  ingress:
    enabled: true
    className: <ingress-class>
    annotations:
      cert-manager.io/cluster-issuer: <cluster-issuer>
      cert-manager.io/private-key-algorithm: ECDSA
      # the Secret also holds the DID's key: a renewal must keep it, or the DID changes and every
      # credential issued with the old key stops verifying
      cert-manager.io/private-key-rotation-policy: Never
    hosts:
      - host: <did-domain>
        paths:
          - path: /
            pathType: ImplementationSpecific
    tls:
      - secretName: did-tls
        hosts:
          - <did-domain>

    Credential issuer: Keycloak¶

    Keycloak issues the provider's own users their credentials and signs them with the DID's key: the prepare-keystore init container turns the DID Secret into the PKCS12 keystore the realm reads. The ingress publishes only /realms/<realm> and /resources; the admin console and the master realm stay inside the cluster. See Keycloak configuration.

    keycloak:
  enabled: true
  keycloak:
    # the public URL, so that Keycloak does not derive it from each request
    hostname: https://<keycloak-domain>
    hostnameStrict: true
  # its own database user, created by the Postgres operator (see managedPostgres below)
  database:
    username: keycloak
    existingSecret: keycloak.postgres.credentials.postgresql.acid.zalan.do
  ingress:
    enabled: true
    className: <ingress-class>
    annotations:
      cert-manager.io/cluster-issuer: <cluster-issuer>
      cert-manager.io/private-key-algorithm: ECDSA
    hosts:
      - host: <keycloak-domain>
        paths:
          # only what wallets need: the realm's endpoints and the static resources. The admin
          # console and the master realm stay inside the cluster (kubectl port-forward).
          - path: /realms/<realm>
            pathType: Prefix
          - path: /resources
            pathType: Prefix
    tls:
      - secretName: keycloak-tls
        hosts:
          - <keycloak-domain>
  # Keycloak signs the credentials with the DID's key: this init container turns the key and
  # certificate of the DID's Secret into the PKCS12 keystore the realm reads
  extraInitContainers:
    - name: prepare-keystore
      image: alpine/openssl:3.5.5
      command: ["/bin/sh", "-c"]
      args:
        - |
          # the CA of the certificate goes into the keystore too, when the Secret has it (a
          # private CA); a public one, such as Let's Encrypt, leaves ca.crt out or empty
          ca=""
          if [ -s /certs-did/ca.crt ]; then ca="-certfile /certs-did/ca.crt"; fi
          openssl pkcs12 -export \
            -in /certs-did/tls.crt \
            -inkey /certs-did/tls.key \
            $ca \
            -out /did-material/cert.pfx \
            -name "didPrivateKey" \
            -passout env:STORE_PASS
          chmod 644 /did-material/cert.pfx
      env:
        - name: STORE_PASS
          valueFrom:
            secretKeyRef:
              name: keystore-password
              key: password
      volumeMounts:
        - name: did-material
          mountPath: /did-material
        - name: did-key
          mountPath: /certs-did
          readOnly: true
  extraVolumeMounts:
    # Keycloak only reads realm keystores from /opt/keycloak/data/<realm name>
    - name: did-material
      mountPath: /opt/keycloak/data/<realm>
    - name: realms
      mountPath: /opt/keycloak/data/import
  extraVolumes:
    - name: did-material
      emptyDir: {}
    # the realm the chart renders, in the ConfigMap <realm name>-realm
    - name: realms
      configMap:
        name: <realm>-realm
    - name: did-key
      secret:
        secretName: did-tls
  # replaces the chart's list: keep KC_HEAP_SIZE
  extraEnvVars:
    - name: KC_HEAP_SIZE
      value: "1024m"
    - name: STORE_PASS
      valueFrom:
        secretKeyRef:
          name: keystore-password
          key: password
  issuerDid: <did>
  signingKey:
    storePath: /opt/keycloak/data/<realm>/cert.pfx
    storePassword: "${STORE_PASS}"
    keyAlias: didPrivateKey
    keyPassword: "${STORE_PASS}"
    did: <did>
    keyAlgorithm: ES256
  realm:
    name: <realm>
    frontendUrl: https://<keycloak-domain>
    import: true
    # The provider's own staff get credentials too, for example to manage the provider's offers.
    # One credential type, UserCredential, with the roles the user holds at this provider.
    verifiableCredentials:
      user-credential:
        attributes:
          format: jwt_vc_json
          verifiable_credential_type: UserCredential
          credential_signing_alg: ES256
          credential_build_config.token_jws_type: JWT
        protocolMappers:
          - name: context-mapper
            protocol: oid4vc
            protocolMapper: oid4vc-context-mapper
            config:
              context: https://www.w3.org/2018/credentials/v1
          - name: email-mapper
            protocol: oid4vc
            protocolMapper: oid4vc-user-attribute-mapper
            config:
              claim.name: email
              userAttribute: email
          - name: roles-mapper
            protocol: oid4vc
            protocolMapper: oid4vc-target-role-mapper
            config:
              claim.name: roles
              clientId: <did>
          - name: subject-id-mapper
            protocol: oid4vc
            protocolMapper: oid4vc-subject-id-mapper
            config:
              userAttribute: email
              claim.name: id
    # Users are not part of the values: create them in the realm, or federate it.
    clientRoles: |
      "<did>": [
        {
          "name": "REPRESENTATIVE",
          "description": "Acts on behalf of the provider",
          "clientRole": true
        }
      ]
    # the client the roles above belong to, named after the DID. It only holds roles: no login
    # flow is enabled on it.
    clients: |
      {
        "clientId": "<did>",
        "description": "Roles of the users at this provider",
        "enabled": true,
        "protocol": "openid-connect",
        "publicClient": false,
        "standardFlowEnabled": false,
        "implicitFlowEnabled": false,
        "directAccessGrantsEnabled": false,
        "serviceAccountsEnabled": false
      }

    Authentication and authorization¶

    The verifier checks each request's credentials against the Trust Anchor's registry (tirAddress) and the provider's local trusted issuers list, and issues access tokens signed with a persistent RSA key. APISIX is the gateway in standalone mode with its Admin API disabled, OPA decides on the ODRL policies the PAP holds, and each component connects to its own PostgreSQL user. If the certificates in the chain are not publicly trusted, see Trusting a private CA for ssl_verify.

    Signing key¶

    The verifier's token-signing key is a persistent RSA key kept in a Secret, so access tokens stay valid across restarts and replicas.

    extraManifests:
  # the verifier's token signing key: RSA, kept in a Secret so that tokens stay valid across
  # restarts and replicas
  - apiVersion: cert-manager.io/v1
    kind: Certificate
    metadata:
      name: verifier-token-key
      namespace: "{{ .Release.Namespace }}"
    spec:
      secretName: verifier-token-key
      commonName: <verifier-domain>
      dnsNames:
        - <verifier-domain>
      issuerRef:
        name: <cluster-issuer>
        kind: ClusterIssuer
      privateKey:
        algorithm: RSA
        size: 2048

    Optional components¶

    scorpio, tm-forum-api and contract-management are part of the profile because a provider that offers TM Forum products needs them; a provider that only protects a plain data service can set them to false. Other components are optional and off by default: a local marketplace (examples/provider-marketplace.yaml), the Dataspace Protocol connector (DSP Integration), and Vault for production identity material (Production setup for Vault).

    Production considerations¶

    TLS certificates¶

    • All publicly reachable endpoints must use HTTPS with valid TLS certificates issued by a trusted CA
    • You can enable cert-manager directly in the FIWARE DSC Helm chart to automate certificate issuance and renewal

    DID and key management¶

    • Use a registered domain name that your organization controls for the did:web identifier
    • Ensure the DID document is served over HTTPS with a valid certificate
    • Protect the private key associated with your DID: it is the foundation of your organization's identity in the data space. If compromised, an attacker could issue credentials on your behalf

    Identity key lifecycle¶

    The DID's private key is what did-helper publishes and what Keycloak signs credentials with. If it changes, the DID document changes with it, every credential signed with the previous key stops verifying, and the participants that resolved the DID see a different key without notice.

    Since cert-manager 1.18, a certificate's privateKey.rotationPolicy defaults to Always: every renewal - every 60 days with Let's Encrypt - generates a new key. Whatever certificate holds the DID's key must therefore set Never. There are two ways to do it:

    • On the DID's Ingress, as the example above does: the cert-manager.io/private-key-rotation-policy: "Never" annotation makes cert-manager keep the key of the certificate it issues for that Ingress, and the same Secret serves TLS and holds the identity key. It is the smallest change, but ties the identity to that Ingress: changing its controller, host or issuer touches the identity key too.
    • A dedicated Certificate for the identity, separate from any Ingress, which only cert-manager renews and which keeps its key. Mount its Secret in did-helper and in the Keycloak keystore init container (Keycloak guide) instead of the Ingress' one; the Ingresses keep their own certificates, so a TLS rotation or compromise does not reach the identity:
    apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: identity-key
  namespace: <your_namespace>
spec:
  secretName: <your_identity_key_secret>
  commonName: <your_did_domain>
  dnsNames:
    - <your_did_domain>
  issuerRef:
    name: <your_cluster_issuer>
    kind: ClusterIssuer
  privateKey:
    algorithm: ECDSA
    size: 256
    rotationPolicy: Never      # renewals keep the key, and with it the DID

    Either way, every component that holds a copy of the key has to follow it: restarting did-helper and Keycloak on a changed Secret keeps them consistent, but credentials signed with a previous key still stop verifying, and a component that stored the key elsewhere - such as the identity hub, in Vault - keeps the old one. Hence Never.

    Use separate keys for everything else that signs, such as the verifier's request objects (clientIdentification) and tokens (see VCVerifier): sharing the identity key spreads it across components that do not need it. The local marketplace needs no key of its own when it logs users in through the verifier's OpenID Connect discovery, as Running a local marketplace describes; its SIOP mode, instead, has to sign with the identity key itself, since the verifier checks those signatures against the DID.

    Keep a backup of the identity key outside the cluster: losing it means a new DID. Rotating it on purpose works the same way as losing it - did-helper publishes a single key - so plan it as a re-issuance of the credentials signed with the old one, as described for the identity hub in Vault.

    Do not expose internal APIs¶

    The following ingresses are useful for development but must not be publicly accessible in production: - Scorpio Broker direct ingress — all access must go through APISIX - ODRL-PAP ingress — policy management should be restricted to authorized operators - Trusted Issuers List management API — restrict to internal access - VCVerifier configuration API (vcverifier.configIngress, port 8090) — it defines which credentials each service accepts; keep it internal, and only publish it, restricted, if services have to be managed from outside the cluster

    APISIX configuration¶

    • Publish the gateway through its Ingress (decentralizedIam.odrlAuthorization.apisix.ingress), which carries the host and TLS. Its Service is a ClusterIP one by default; making it a NodePort or LoadBalancer (apisix.service.type) opens the gateway outside of the Ingress as well
    • APISIX's etcd is only deployed when apisix.etcd.enabled is set, and only needed in a mode that reads the configuration from it, such as traditional with config_provider: etcd (the mode the routes registered through the Admin API need). The default standalone mode reads the routes from a ConfigMap. A mode that needs etcd without one fails to render
    • Change the APISIX admin credentials from defaults
    • Configure proper error responses (do not leak internal service details)
    • Keep ssl_verify: true in the openid-connect plugin. Even when discovery points to the verifier inside the cluster, the discovery document announces the verifier's public jwks_uri, so APISIX fetches the keys that validate every token over HTTPS. Without verification, whoever can intercept that call can make APISIX accept forged tokens.

    Trusting a private CA¶

    If the verifier's certificate is issued by a private CA, give APISIX that CA instead of disabling the verification. Put the CA certificate (PEM) in a Secret, for example private-ca with the key ca.crt, and point the apisix chart to it:

    decentralizedIam:
  odrlAuthorization:
    apisix:
      apisix:
        ssl:
          enabled: true              # the chart only mounts the CA together with its HTTPS listener
          existingCASecret: private-ca
          certCAFilename: ca.crt

    The apisix chart only mounts the CA, and sets it as APISIX's ssl_trusted_certificate, when apisix.ssl.enabled is set, which also opens its HTTPS listener (port 9443); that listener needs no further configuration when TLS is terminated at the Ingress.

    VCVerifier¶

    • Configure the tirAddress to point to the production Trust Anchor's TIR endpoint
    • Ensure the VCVerifier can reach the Trust Anchor over HTTPS with valid certificates
    • If using a proxy, configure HTTPS_PROXY/NO_PROXY appropriately
    • The VCVerifier's signing key (used for JWT issuance) must be protected

    Metrics¶

    The verifier serves its Prometheus metrics, /metrics, on port 9090 of the verifier Service (metrics), apart from port 3000, which its Ingress publishes, so the metrics are not reachable from outside the cluster. Scrape them from inside the cluster, at http://verifier.<your_namespace>.svc.cluster.local:9090/metrics. The port is set with deployment.server.metricsPort; setting it to the main port (3000) serves the metrics there again, and publishes them with the Ingress.

    Request object modes¶

    deployment.verifier.supportedModes defaults to urlEncoded. With byValue or byReference the verifier signs the request objects it sends to wallets, so it also needs clientIdentification; without its keyPath the verifier does not start (Failed to initialize verifier):

    decentralizedIam:
  vcAuthentication:
    vcverifier:
      deployment:
        verifier:
          supportedModes: ["byValue", "byReference"]
          clientIdentification:
            id: x509_san_dns:<your_verifier_domain>   # how the verifier identifies itself to wallets
            keyPath: /signing-key/tls.key            # key that signs the request objects
            certificatePath: /signing-key/tls.crt    # certificate embedded in their header
            requestKeyAlgorithm: ES256               # algorithm of that key
        additionalVolumes:
          - name: signing-key
            secret:
              secretName: <your_verifier_domain>-tls # e.g. a cert-manager certificate for the verifier's domain
        additionalVolumeMounts:
          - name: signing-key
            mountPath: /signing-key

    The verifier reads the algorithm from requestKeyAlgorithm; the keyAlgorithm listed under clientIdentification in the vcverifier chart's values has no effect.

    Token signing algorithm¶

    The access tokens the verifier issues are validated by APISIX's openid-connect plugin, whose library (lua-resty-openidc) only accepts tokens signed with RS* or HS* algorithms, in every APISIX version up to 3.19 at least. With an ES256 token it does not look up any key - neither in the JWKS nor in an x5c chain - and rejects every request with 401 and jwt signature verification failed: No trusted certs loaded. Keep deployment.verifier.keyAlgorithm at its default RS256 for every verifier whose tokens APISIX validates. This only concerns the verifier's tokens; Keycloak can keep signing credentials with ES256.

    By default (generateKey: true) the verifier generates that key at startup and only keeps it in memory, so the tokens issued before a restart stop validating and several replicas do not share a key. In production, provide an RSA key instead, with generateKey: false and keyPath.

    Policy management¶

    • Define ODRL policies following the principle of least privilege
    • Consider versioning your policies (store them in version control and apply via CI/CD)

    Central Marketplace integration¶

    If the provider participates in a Central Marketplace:

    • The Contract Management host exposed through APISIX must be reachable from the Central Marketplace over HTTPS with a valid certificate. The contractManagement.address registered in the provider's Organization at the marketplace must match this host exactly: no trailing paths, and the scheme/port used when registering must remain valid from the marketplace's network.
    • Coordinate version upgrades with the Central Marketplace operator: changes in the contract-management notification contract require both sides to be aligned. Keep the minimum versions noted in Participating in a Central Marketplace as a floor.
    • Keep the local Trusted Issuers List aligned with the Central Marketplace's MarketplaceCredential issuer. If the marketplace rotates its DID, the provider will stop accepting notifications until the TIL and the Trust Anchor's TIR are updated.

    Upgrade strategy¶

    • Review the FIWARE Data Space Connector release notes before each upgrade for breaking changes
    • Keep the connector version aligned across all participants in the data space when possible to avoid protocol incompatibilities
