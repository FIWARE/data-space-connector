    Release 10.x.x¶

    Version 10.x.x of the Data Space Connector contains a major change to the Keycloak deployment and to the OID4VCI realm model. They will be listed below, together with required actions for migration.

    The two drivers of this release are:

    1. The Bitnami Keycloak Helm chart was withdrawn, so the umbrella now depends on the CloudPirates Keycloak chart. The CloudPirates chart targets the upstream Quarkus image (quay.io/keycloak/keycloak) and exposes a different values.yaml shape than Bitnami's, so the entire keycloak: configuration block must be rewritten.
    2. Keycloak 26.4 redesigned OID4VCI (keycloak/keycloak#39768). The realm-attribute scheme vc.<name>.* and the components.CredentialBuilder block are gone; per-credential configuration moved to ClientScope attributes on scopes with protocol: "oid4vc", and several mapper config keys were renamed or removed. The DSC chart's realm.verifiableCredentials API has been adjusted accordingly.

    10.22.0 — APISIX upgraded to chart v3¶

    • decentralized-iam bumped to 3.0.0, which brings odrl-authorization 3.0.0 and with it the APISIX sub-chart's major upgrade from chart 2.x to v3. The APISIX gateway app version is unaffected; only the APISIX chart's own contract changes. This chart's values keep working: the DSC only sets decentralizedIam.odrlAuthorization.apisix to disable the ingress controller, disable etcd and scrape Prometheus — none of those keys changed.
    • No default Admin API key anymore. APISIX chart v3 stops shipping the public default admin keys and generates a random one into a Secret instead. On a fresh install (the local k3s deployment and any new release) this is transparent — nothing to do. On an in-place helm upgrade of an existing release the chart preserves the key via lookup, but the upgrade must run with Helm 3.8+ and must not use --reuse-values (re-pass the full values, or use --reset-then-reuse-values on Helm 3.14+). GitOps/helm template renders without cluster access should pin a key with decentralizedIam.odrlAuthorization.apisix.apisix.admin.credentials.secretName.
    • See the odrl-authorization 3.0.0 release note for the full APISIX migration details.

    10.21.0 — Marketplace on the Business API Ecosystem 2026.10.20 release¶

    • The marketplace runs the components of the Business API Ecosystem release 2026.10.20. The business-api-ecosystem subchart was bumped to 1.3.1, which deploys the logic proxy 11.25.3 (was 11.20.3) and the charging backend 11.9.1 (was 11.7.0). Both only add optional settings: existing values keep working.
    • The logic proxy builds the user's profile from the credential (it needs 11.22.0 or later). If your values pin marketplace.bizEcosystemLogicProxy.statefulset.image.tag to an older version, as the local marketplace guide suggested, remove the pin.
    • The charging backend can be auto-instrumented. It now runs Python 3.9, and the chart gives it the Django settings its instrumentation loads before the application starts. Annotate it with instrumentation.opentelemetry.io/inject-python: "true" in marketplace.bizEcosystemChargingBackend.deployment.additionalAnnotations (see Observability).
    • Python auto-instrumentation exports its spans. The Python agent of the OpenTelemetry Operator ships no gRPC exporter, but the Instrumentation set gRPC for every language, so injected Python workloads exported nothing. Python now uses OTLP/HTTP, by default to port 4318 of the bundled collector; set tracing.autoInstrumentation.python.endpoint if you export to another collector. Java and Node.js keep gRPC.
    • The default Python agent is 0.61b0 (was 0.62b1). 0.62b1 bundles a urllib3 that needs Python 3.10, and broke the start of Python 3.9 workloads such as the charging backend.

    The charging backend keeps its data in MongoDB: the new version adds collections and fields, and existing data needs no migration.

    10.20.7 — Reference profiles¶

    • Reference profiles to start a real deployment from. charts/data-space-connector/examples/ has example values files for a provider (provider.yaml, plus provider-marketplace.yaml for the provider's own local marketplace, not the Central Marketplace) and a consumer (consumer.yaml), and charts/trust-anchor/examples/ one for the trust anchor, to adapt to your installation. Their README lists the prerequisites, the placeholders to replace, the Secrets to create and the installation steps.

    The charts do not change. No migration is required.

    10.20.2 — Configurable database name and port for Scorpio¶

    • The Scorpio broker can now be pointed at a database with a non-default name and port. The scorpio-broker-aaio subchart was bumped to 0.6.0, which adds scorpio.db.name and scorpio.db.port. Both are empty by default, so Scorpio keeps using its built-in defaults (database ngb on port 5432) and the rendered manifests do not change. Set them to connect Scorpio to a differently named database or a non-standard port.

    No migration is required.

    10.20.1 — Upgrades with cert-manager, and auto-instrumentation on a first install¶

    • Upgrading a release with cert-manager.enabled no longer hangs. The chart runs cert-manager's startupapicheck job on every upgrade, but its service account, Role and RoleBinding were only created on install and deleted afterwards. On an upgrade the job could not start its pod (serviceaccount "<release>-cert-manager-startupapicheck" not found), and helm upgrade waited until it timed out (post-upgrade hooks failed: ... startupapicheck not ready). They are now created again on every upgrade.
    • Auto-instrumentation installs at the first attempt. With tracing.autoInstrumentation.enabled and the opentelemetry-operator subchart in the same release, a first helm install failed with resource mapping not found ... kind "Instrumentation", since the operator's chart installs that CRD as a template. The Instrumentation is now a post-install/post-upgrade hook: a new <release>-otel-webhook-wait job waits for the operator's webhook, then the Instrumentation is created, and then the annotated pods are restarted, as before.
    • The default Python agent (tracing.autoInstrumentation.python.image) was autoinstrumentation-python:0.54b0, which is no longer published: a pod annotated for Python injection stayed in ImagePullBackOff, and its rollout never finished. It is now 0.62b1, the last one that supports Python 3.9 (later ones require 3.10). The marketplace charging backend runs Python 3.9 from 11.8.3 on; the 11.7.0 that the marketplace chart deploys runs Python 3.8, which no published agent supports, so do not annotate it for injection.

    The local environment in k3s/ gets its monitoring and gaia-x scenarios working again. The monitoring profile lost the provider's environment variables of contract management and the marketplace, and the gx-registry never started. The provider profile now sets the logic proxy's purchase and SIOP client through purchaseEnabled and siop.clientId instead of additionalEnvVars. The chart already renders those two variables, and the duplicates made an upgrade fail with The order in patch list doesn't match $setElementOrder list.

    Upgrading¶

    On the upgrade, Helm removes the Instrumentation from the release and the new hook creates it again; the annotated pods are restarted with the agent, as on every upgrade. From then on it is a hook resource:

    • helm uninstall no longer deletes it. Remove it afterwards with kubectl delete instrumentation -n <namespace> <release>-auto-instrumentation.
    • To roll back to an earlier version, delete it first: an earlier version manages it as a regular resource and refuses to take over one it did not create (invalid ownership metadata).

    10.20.0 — The chart's MongoDB runs as a service account of its own¶

    The pods of the MongoDB that the chart deploys (managedMongo) ran as the operator's mongodb-database service account. The operator's chart creates it in a single namespace only (its database.namespace), so a connector in any other namespace had to create it by hand, and its MongoDB stayed Pending without it (serviceaccounts "mongodb-database" not found).

    The chart now creates a service account of its own, <release>-mongodb, with the same Role and RoleBinding, and runs the MongoDB pods as it (managedMongo.serviceAccount). Under another name it never collides with the operator's, wherever that is created.

    • managedMongo.serviceAccount.name changes its name.
    • managedMongo.serviceAccount.create: false with a name runs the pods as a service account you manage yourself; without a name, as the operator's mongodb-database, as before.
    • A serviceAccountName set in managedMongo.spec.statefulSet still wins.

    Upgrading¶

    The operator updates the MongoDB StatefulSet to the new service account, so its pod restarts once during helm upgrade. With the default single member, the marketplace loses its database for that restart; the data stays in the volume.

    The operator's mongodb-database in the connector's namespace is no longer used. If you created it by hand, you can delete it:

    kubectl delete rolebinding,role,serviceaccount -n <namespace> mongodb-database

    If the operator's chart created it (database.namespace set to the connector's namespace), leave it or drop that setting from the operator's release.

    10.19.0 — No unused users in the managed PostgreSQL¶

    The PostgreSQL that the chart deploys with decentralizedIam.vcAuthentication.managedPostgres no longer gets these users, which nothing connected with:

    • admin, a superuser with createdb;
    • issuer, with its issuer database.

    The managed PostgreSQL of the trust-anchor chart (managedPostgres) no longer gets its admin superuser either. Each component keeps its own user and database (til, ccs, pap, keycloak, and ih for the IdentityHub), and the operator still creates its own postgres superuser.

    decentralized-iam 2.3.0 brings vc-authentication 1.6.0, which drops admin from its defaults as well, together with credentials-config-service 2.7.1 and trusted-issuers-list 0.19.2.

    Scorpio sets QUARKUS_FLYWAY_SCHEMAS=public and QUARKUS_FLYWAY_DEFAULT_SCHEMA=public by default (in scorpio.additionalEnvVars). Its migrations already name the public schema, so this changes nothing when it connects as postgres. It lets Scorpio connect with the owner user of a prepared database, whose search path Flyway would otherwise read as a schema name:

    decentralizedIam:
  vcAuthentication:
    managedPostgres:
      config:
        preparedDatabases:
          ngb:
            defaultUsers: true
            schemas:
              public: {}
            extensions:
              postgis: public
scorpio:
  db:
    user: ngb_owner_user
    existingSecret:
      enabled: true
      name: ngb-owner-user.postgres.credentials.postgresql.acid.zalan.do
      key: password

    A list given in scorpio.additionalEnvVars replaces the default one, so add the two variables to it if you set your own.

    The profiles in k3s/ (local and test environments) now connect each component with its own user instead of postgres, and Scorpio with ngb_owner_user as above. The chart's defaults still use postgres.

    Required action: drop the unused users of an existing cluster¶

    The Zalando operator does not drop the users and databases that disappear from the postgresql resource, so an existing cluster keeps them after helm upgrade. Drop them by hand, in the connector's cluster (postgres, in the release's namespace):

    kubectl exec -n <namespace> postgres-0 -- psql -U postgres -c 'DROP ROLE admin;'
kubectl exec -n <namespace> postgres-0 -- psql -U postgres -c 'DROP DATABASE issuer;'
kubectl exec -n <namespace> postgres-0 -- psql -U postgres -c 'DROP ROLE issuer;'
kubectl delete secret -n <namespace> \
  admin.postgres.credentials.postgresql.acid.zalan.do \
  issuer.postgres.credentials.postgresql.acid.zalan.do

    and in the Trust Anchor's:

    kubectl exec -n <namespace> postgres-0 -- psql -U postgres -c 'DROP ROLE admin;'
kubectl delete secret -n <namespace> admin.postgres.credentials.postgresql.acid.zalan.do

    If you connected anything with one of them, keep it in managedPostgres.config.users (and databases) instead: DROP ROLE fails for a user that still owns objects.

    10.17.0 — APISIX: a ClusterIP gateway, etcd only when used, no catch-all route¶

    decentralized-iam 2.2.0 brings odrl-authorization 2.5.0, which changes three defaults of the data service gateway (all under decentralizedIam.odrlAuthorization.apisix):

    Value Before Now
    service.type NodePort ClusterIP
    etcd.enabled true false
    catchAllRoute.enabled true false
    • As a NodePort, the gateway also answered plain HTTP on a port of every node, outside of the Ingress that carries its host and TLS. It is now published through its Ingress only.
    • The default standalone mode reads the routes from a ConfigMap and never connected to etcd. That etcd ran three replicas of bitnamilegacy/etcd:latest without authentication, each on an 8Gi volume, and held APISIX back with a wait-etcd init container.
    • The catch-all route sent every unmatched path (/*) to my-broker:8080, which does not exist.

    The same release brings the apisix chart 2.18.2 (APISIX 3.17.0 → 3.19.0) and odrl-pap 1.8.1.

    The keys decentralizedIam.odrlAuthorization.opa.{enabled,resourceUrl,port,policies,methods,data} are removed: odrl-authorization never read them, and reads the OPA sidecar's settings from opa.config instead. Setting one now fails the render.

    Breaking changes¶

    These apply on helm upgrade:

    • Traditional mode: APISIX in a mode that reads its configuration from etcd (a mode other than standalone, unless the role is traditional with config_provider: yaml) fails to render without an etcd, naming the values to set. The upgrade stops before changing anything. Set decentralizedIam.odrlAuthorization.apisix.etcd.enabled: true, or apisix.externalEtcd.host to an etcd of your own. The provider, consumer-auth and consent-trust-anchor profiles in k3s/ do the former.
    • NodePort: whatever reached the gateway on a port of the nodes has to go through its Ingress (decentralizedIam.odrlAuthorization.apisix.ingress), or set decentralizedIam.odrlAuthorization.apisix.service.type: NodePort.
    • Catch-all route: a deployment that used it, with its own upstream, sets decentralizedIam.odrlAuthorization.apisix.catchAllRoute.enabled: true.
    • Removed OPA keys: move what was set there under decentralizedIam.odrlAuthorization.opa.config, or drop it; it never had an effect.

    Required action: the etcd volumes of a standalone APISIX¶

    Upgrading a release that runs APISIX in the default standalone mode removes the etcd StatefulSet, but Kubernetes keeps the PersistentVolumeClaims it created, one per replica (three by default). Once the upgrade is done, delete them:

    kubectl delete pvc -n <namespace> data-<release>-etcd-0 data-<release>-etcd-1 data-<release>-etcd-2

    10.16.0 — Safer defaults for the Keycloak realm¶

    The realm the chart imports by default no longer comes with a known login, nor with the password grant on its public clients, and it takes plain HTTP only from private addresses:

    Value Before Now
    keycloak.realm.sslRequired none external: HTTPS for requests from public addresses
    keycloak.realm.defaultClients.account-console.directAccessGrantsEnabled true false
    keycloak.realm.defaultClients.admin-cli.directAccessGrantsEnabled true false
    keycloak.realm.users admin-user, password test none
    keycloak.realm.clientRoles ADMIN on the connector's own client (${DID}) none

    In a deployment that did not replace them, anyone could log in as admin-user with the password in this repository and get a credential with the ADMIN role, issued by the organisation; with the password grant on the public clients, a single request to the token endpoint was enough. A map of client roles was merged into the default one, so the ADMIN role also reached deployments that declared their own roles as a map.

    Besides, a default client set to null (keycloak.realm.defaultClients.admin-cli: null) is now left out of the realm; it failed the render before. See Keycloak.

    Breaking changes¶

    Keycloak imports the realm only when it does not exist, so an existing realm does not change. The new defaults apply to realms created from now on, including a reinstallation.

    • Users and client roles: a deployment that relied on admin-user or on the ADMIN role of the defaults declares them in keycloak.realm.users and keycloak.realm.clientRoles.
    • Password grant: whatever logs in with a user's password through account-console or admin-cli fails with unauthorized_client. People log in through the browser or get their credentials with a wallet; components use a confidential client of their own with the client credentials grant, as the vc-operator does (vcCredentials). The credentials helper that logged in this way is no longer part of the chart; the Central Marketplace guide shows its replacement. To turn the grant back on for one client:
    keycloak:
  realm:
    defaultClients:
      account-console:
        directAccessGrantsEnabled: true

    The k3s profiles do this, because the integration tests and doc/scripts/get_credential.sh use it. - HTTPS: a realm whose frontend URL (keycloak.realm.frontendURL) is plain HTTP answers HTTPS required to requests from public addresses. Calls from private addresses, such as the components inside the cluster calling http://<release>-keycloak:8080, keep working. Keycloak takes the client address from the X-Forwarded-For header of the ingress, and the scheme from the frontend URL, so a realm with an https frontend URL is not affected; refusing plain HTTP there is up to the ingress. To go back to accepting HTTP from anywhere, set keycloak.realm.sslRequired: none.

    Required action: existing realms¶

    An existing realm keeps admin-user and its password. Unless it is deliberately in use, delete the user, or at least change its password, in the Keycloak admin console (realm, Users). The other settings can be applied there too:

    • Realm settings → General → Require SSL: external requests;
    • Clients → account-console and admin-cli → Capability config: clear Direct access grants.

    10.15.1 — OID4VP clients accept the verifier's own state¶

    Since 6.24.2, the VCVerifier puts its own session id in the state of the authorization request, instead of echoing the one the client sent. oid4vp-client-lib up to 0.0.6 rejected that request with Authorization request contains wrong state., so with the VCVerifier 6.27.0 of 10.15.0 no component that authenticates through the library could obtain an access token from a verifier. That broke the OID4VC contract negotiation of fdsc-edc, the order processing of contract-management in a central marketplace, and the consent-facade's access to the provider's TM Forum APIs.

    oid4vp-client-lib 0.0.7 no longer checks the state, and the following charts carry it:

    Chart Version Image
    fdsc-edc 0.7.6 → 0.7.8 1.8.4 → 1.8.5
    contract-management 3.6.0 → 3.6.2 3.4.0 → 3.4.1
    consent-facade 0.2.0 → 0.2.1 0.0.14 → 0.4.2

    10.14.0 — IdentityHub startup probe¶

    IdentityHub now has a startup probe on its liveness endpoint, configured under identityhub.startupProbe and enabled by default. It gives IdentityHub up to 5 minutes to start (30 checks, every 10 seconds) before the liveness probe takes over.

    Before, the liveness probe gave it about 35 seconds. When the node was busy starting the rest of the release, IdentityHub was killed before it had started and went into a restart loop, and its deployment could exceed its progress deadline. A restart in the middle of the first start could also leave the super-user with an API key other than identityhub.superuser.key: IdentityHub seeds the super-user only when it does not exist yet, so every call to the Identity API was rejected with 401 Invalid API token. To repair such a deployment, delete the super-user participant context from the IdentityHub database and restart IdentityHub.

    No action is required. Set identityhub.startupProbe.enabled: false to keep the previous behaviour.

    Required action: existing IdentityHub deployments¶

    IdentityHub migrates its database by itself on start. Back up the database and the vault first: going back means restoring both.

    IdentityHub's migrations do not carry existing rows forward, so an upgraded deployment starts, reports healthy and is unusable. Four tables are affected, and they surface one at a time — each fix only reveals the next — so run all four statements in one go, after the first start on the new image. Tracked upstream as tractusx-identityhub#371.

    -- 1. participant contexts have no configuration row: every authenticated Identity API call
--    returns 500 with `No configuration found for participant context super-user`
INSERT INTO edc_participant_context_config
  (participant_context_id, created_date, last_modified_date, entries, private_entries)
SELECT participant_context_id,
       (extract(epoch from now())*1000)::bigint,
       (extract(epoch from now())*1000)::bigint,
       '{}', '{}'
FROM participant_context
ON CONFLICT (participant_context_id) DO NOTHING;

-- 2. STS clients are not linked to their participant context (column defaults to ''):
--    POST /api/sts/token returns 500 with the same exception and an EMPTY context id
UPDATE edc_sts_client SET participant_context_id = id WHERE participant_context_id = '';

-- 3. key pairs have no usage (column defaults to '', but it holds a JSON array):
--    `MismatchedInputException: No content to map due to end-of-input` in SqlKeyPairResourceStore
UPDATE keypair_resource SET usage = '["sign_token","sign_presentation"]'
 WHERE usage = '' OR usage IS NULL;

-- 4. credential usage default is lower-case, the enum constant is not:
--    `No enum constant CredentialUsage.holder`
UPDATE credential_resource SET usage = 'Holder' WHERE usage = 'holder';
ALTER TABLE credential_resource ALTER COLUMN usage SET DEFAULT 'Holder';

    Empty entries in (1) is enough; the row only has to exist. The bootstrap Job retries on its own and completes once (1) and (2) are in place.

    Then the DID document: it keeps the CredentialService endpoint it was published with, which carries the participant id in base64url. The bootstrap Job does not rewrite it for a participant that already exists, so every DCP presentation query against it returns 404 (Object of type IdentityHubParticipantContext with ID=<base64> was not found) and the counterparty reports a bare 401. Either start IdentityHub on an empty database and vault, so the bootstrap Job registers the participant again, or replace the endpoint.

    PATCH is documented as the replace operation but appends on 0.5.0-rc1, leaving two entries with the same id — resolvers then pick the stale one and nothing appears to change. Delete and re-add instead (the {did} segment of both calls stays base64url, while {participantContextId} is URL-encoded):

    DID=did:web:mp-operations.org
CTX=$(printf '%s' "$DID" | sed 's/:/%3A/g')
B64=$(printf '%s' "$DID" | base64 | tr '+/' '-_' | tr -d '=\n')

# removes every entry with that id, including the stale one
curl -X DELETE "${IDENTITY_API}/participants/${CTX}/dids/${B64}/endpoints?serviceId=credential-service&autoPublish=false" \
  -H "x-api-key: ${SUPERUSER_API_KEY}"

curl -X POST "${IDENTITY_API}/participants/${CTX}/dids/${B64}/endpoints?autoPublish=true" \
  -H "x-api-key: ${SUPERUSER_API_KEY}" -H 'Content-Type: application/json' \
  -d "{\"id\":\"credential-service\",\"type\":\"CredentialService\",\"serviceEndpoint\":\"${CREDENTIAL_SERVICE_URL}/api/credentials/v1/participants/${CTX}\"}"

    Verify the published document ends up with exactly one credential-service entry, and that the verification method still carries the same public key it had before the upgrade — if the key changed, the bootstrap re-derived an identity and every counterparty's trust list is now stale.

    10.10.0 — eIDAS 2.0 validation moves into VCVerifier¶

    The external dss-validation-service is no longer how eIDAS certificate chains are checked. VCVerifier validates them itself, with PKIX chain building against a trust store it builds from the EU List of Trusted Lists (ETSI TS 119 612). This release pins decentralized-iam 2.1.23 -> 2.1.25 (vcverifier subchart 4.15.3, VCVerifier 6.23.1). 10.9.0 already shipped 2.1.23, which carries the validation itself but spells the LOTL override lotUrl

    Full documentation: eIDAS 2.0 Compliance. Decision record: ADR-0006.

    Off by default¶

    decentralizedIam:
  vcAuthentication:
    vcverifier:
      deployment:
        eidas:
          enabled: false

    An existing release upgrades to a no-op. Nothing is fetched and no credential changes behaviour until the block is switched on.

    Two mechanisms, different triggers¶

    eidas.enabled builds the trust store. What then consults it depends on the issuer:

    Mechanism Trigger Covers Formats
    did:elsi proof check iss is a did:elsi: DID x5c chain + organizationIdentifier ↔ DID match any
    EidasValidationService credential type carries eidasConfig.enabled: true x5c chain + per-type allowedCountries / requireQualified SD-JWT only

    A did:elsi deployment gets validation from eidas.enabled alone. A did:web or HTTPS issuer does not: those resolve their key from the DID document or JWKS and the x5c header is ignored by the proof check, so without eidasConfig on an SD-JWT type the trust lists are fetched on every refresh and never consulted — with nothing failing to indicate it.

    eidasConfig is also the only source of per-type country and qualified-service filters; the did:elsi path searches all countries and applies no qualified filter.

    SD-JWT only¶

    EidasValidationService is implemented for dc+sd-jwt and nothing else. A jwt_vc_json credential with eidasConfig.enabled: true is rejected outright with ErrorEidasSDJWTRequired — not skipped. This constraint applies to that mechanism only; the did:elsi proof check works for any format.

    The shipped eIDAS overlay now issues dc+sd-jwt so that both mechanisms apply, and the DCQL query matching them uses meta.vct_values (flat array) instead of meta.type_values.

    Breaking changes¶

    Change Action
    Maven profile elsi renamed to eidas mvn clean deploy -Plocal,elsi → -Plocal,eidas. Maven does not fail on an unknown profile id, so the old invocation silently deploys without the overlay.
    k3s/provider-elsi.yaml deleted, k3s/consumer-elsi.yaml renamed Use k3s/provider-eidas.yaml / k3s/consumer-eidas.yaml.
    decentralizedIam.vcAuthentication.dss deprecated No effect once eidas.enabled is true. Remove it at your convenience.
    verifier.elsi.validationEndpoint gone Removed upstream in vcverifier 4.13.0; see the Rollback notes — reverting needs a dependency pin, not a values change.

    lotlUrl, not lotUrl¶

    Up to decentralized-iam 2.1.24 the vcverifier subchart declared the LOTL override as lotUrl while the server read lotlUrl, so the subchart's own key was inert. 2.1.25 renames it, and there is no backward-compatible alias: a values file that still sets

          lotUrl: "https://..."     # no longer a thing

    is silently ignored and the verifier falls back to the official EU LOTL. Rename it to lotlUrl. Deployments that already worked around this by setting lotlUrl need no change.

    Chart-side detail: jades.enabled is not a vc. attribute¶

    dsc.vcClientScopes prefixes every credential attribute with vc., which is right for Keycloak's CredentialScopeModel but wrong for jades.enabled — the keycloak-jades-vc-issuer plugin reads that one raw via clientScope.getAttribute("jades.enabled").     10.8.0 — policies on the ServiceSpecifications a product is composed of¶

    contract-management can now read the ODRL policies and the credential configuration from the ServiceSpecifications a ProductSpecification is composed of, instead of only from the ProductSpecification itself. An access policy protects an API, and an API is a ServiceSpecification - so a provider composing one product out of three services can author three policies where they belong, and an order for that product activates all of them.

    Off by default¶

    contract-management:
  enableSpecificationComposition: false
  specificationCompositionMaxDepth: 2

    Enabling it changes which configuration an order activates, so it is opt-in per deployment. It also adds one TMForum read per referenced ServiceSpecification to the activation of an order.

    What it does when enabled¶
    Levels read the ordered ProductSpecification, the ServiceSpecifications it references, and recursively the ProductSpecifications it bundles. ResourceSpecifications are not read - they carry no connector configuration.
    Aggregation union, per level. Policies are de-duplicated by odrl:uid, credential configurations by value. Two different policies claiming one odrl:uid fail the activation, because the ODRL-PAP keys an installed policy by that uid.
    Credentials widen the trusted-issuers-list evaluates several configurations of one credential type as an OR, so a permissive part relaxes a restrictive one. Author with that in mind.
    One provider a composition that declares more than one provider fails the activation. A part that declares none inherits the composition's provider.
    Depth specificationCompositionMaxDepth levels; a deeper or cyclic composition is truncated and logged with a warning naming the specification, the skipped references and the limit.
    Broken references a referenced offering, specification, quote or provider that cannot be read now fails the activation with a logged error instead of activating nothing silently.

    Fixed regardless of the flag¶

    Three ways a flat order could already fail are gone:

    • a ProductSpecification without any productSpecCharacteristic, or a characteristic without a valueType, raised a NullPointerException and took the whole order's activation down;
    • an offering that bundles others instead of referencing a specification failed the activation of every other item in the same order;
    • an order that legitimately configures nothing resolved to nothing at all, which the notification listener answered with a 404, which made the TMForum hub redeliver the event.

    Component versions¶

    Component Version Why
    contract-management chart 3.5.36 (app 3.3.12) reads the composed specifications and grants credentials under the id of the order that granted them
    trusted-issuers-list app 0.9.1 the scope-addressed credential endpoints. 0.9.0 carries the API but does not start against MySQL, so 0.9.1 is the first usable release

    Both are delivered by the chart chain: decentralized-iam 2.1.21 brings trusted-issuers-list app 0.9.1 through vc-authentication 1.3.7, and the umbrella depends on decentralized-iam 2.1.22. No image override is needed.

    Behaviour change outside the flag¶

    A single ProductSpecification that declares two different parties in the provider role now fails the activation instead of picking one of them arbitrarily. Which contract-management is responsible was never defined for that shape; refusing to guess is the safer reading. Check for specifications with more than one relatedParty in the role configured as contract-management.organization.provider.role before enabling.

    Required action: move the PKCS12 keystore under data/<realm-name>¶

    Since Keycloak 26.6.4 the java-keystore realm key provider may only read keystores from a directory named after the realm, inside a fixed keystores root — by default ${kc.home.dir}/data, which is /opt/keycloak/data on the official image.     keycloak:
  extraVolumeMounts:
    # directory name MUST equal keycloak.realm.name
    - mountPath: /opt/keycloak/data/test-realm      # was: /did-material
      name: did-material
    - mountPath: /opt/keycloak/data/import
      name: realms
  signingKey:
    storePath: /opt/keycloak/data/test-realm/cert.pfx   # was: /did-material/cert.pfx

    The init container that builds the keystore can keep writing to its own mount of the same emptyDir (/did-material) — only the Keycloak container's view of the file is constrained.

    elsi:
  storePath: /opt/keycloak/data/test-realm/keystore.p12   # was: /trust-store/keystore.p12

    Default account-console client must opt into OID4VCI¶

    KC 26.4+ rejects calls to /protocol/oid4vc/create-credential-offer whose bearer token is issued to a client without oid4vci.enabled=true. Many wallet flows authenticate the user via the built-in account-console client; the umbrella therefore declares the attribute on that client by default:

    keycloak:
  realm:
    defaultClients:
      account-console:
        attributes:
          oid4vci.enabled: "true"

    If you override defaultClients, preserve this attribute.

    OID4VCI realm model rewrite¶

    The realm-attribute scheme realm.attributes vc.<name>.* and the components.CredentialBuilder block are no longer recognised by KC 26.4+. Per-credential configuration is now declared once in realm.verifiableCredentials.<name>; the DSC chart renders one ClientScope per entry with protocol: "oid4vc" and the attributes attached to the scope itself.

    Before (9.x):

    keycloak:
  realm:
    attributes: |
      "vc.user-credential.format": "jwt_vc",
      "vc.user-credential.scope": "UserCredential",
      "vc.user-credential.vct": "UserCredential",
      "vc.user-credential.credential_signing_alg_values_supported": "ES256"
    credentialBuilder:
      jwt-vc-builder:
        id: jwt-vc-builder
        name: jwt_vc

    After (10.x):

    keycloak:
  realm:
    verifiableCredentials:
      user-credential:
        attributes:
          format: "jwt_vc_json"
          verifiable_credential_type: "UserCredential"
          credential_signing_alg: "ES256"
          credential_build_config.token_jws_type: "JWT"
        protocolMappers:
          - name: context-mapper
            protocol: oid4vc
            protocolMapper: oid4vc-context-mapper
            config:
              context: https://www.w3.org/2018/credentials/v1
          - name: email-mapper
            protocol: oid4vc
            protocolMapper: oid4vc-user-attribute-mapper
            config:
              claim.name: email
              userAttribute: email

    The key under verifiableCredentials (user-credential above) is the ClientScope name — i.e. the value the wallet sends as credential_configuration_id. The realm-level realm.credentialBuilder: block is removed entirely (in KC 26.4+ credential builders are loaded via SPI service-loader, not declared per realm).

    Format strings rename¶

    Format 9.x value 10.x value
    SD-JWT VC vc+sd-jwt dc+sd-jwt
    JWT-VC JSON jwt_vc jwt_vc_json

    Template auto-derivations (DSC chart)¶

    The DSC _realm.tpl template fills in two ClientScope attributes when they are not set explicitly:

    • vc.issuer_did — derived from elsi.did if elsi.enabled: true, else from keycloak.issuerDid, else ${DID}. Sets the iss claim of every issued JWT VC.
    • vc.supported_credential_types — defaults to the value of vc.verifiable_credential_type. Drives the type array of JWT-VC JSON credentials and the metadata credential_definition.type. Override it explicitly under attributes if you need a different value than the SD-JWT vct.

    Mapper Old key (9.x) New key (10.x)

    oid4vc-user-attribute-mapper, oid4vc-target-role-mapper, oid4vc-static-claim-mapper, oid4vc-generated-id-mapper, oid4vc-issued-at-time-claim-mapper subjectProperty claim.name

    SD-JWT red list¶

    KC 26.4+ enforces a "red list" of standard claims that must not be undisclosed in a SD-JWT VC: iss, iat, nbf, exp, cnf, vct, status (source: core/src/main/java/org/keycloak/sdjwt/DisclosureRedList.java).

    If you override verifiableCredentials.<name>.attributes.credential_build_config.sd_jwt.visible_claims, include those seven names alongside your domain-specific ones, otherwise issuance fails with IllegalArgumentException: UndisclosedClaims contains red listed claim names.

    keycloak:
  realm:
    verifiableCredentials:
      user-sd:
        attributes:
          format: "dc+sd-jwt"
          verifiable_credential_type: "LegalPersonCredential"
          credential_build_config.sd_jwt.visible_claims: "iss,iat,nbf,exp,cnf,vct,status,roles,email"

    New feature flags¶

    KC main has split the original experimental OID4VCI feature flag into one base flag plus two sub-features. All three must be enabled for the DSC's issuance flow to work:

    keycloak:
  features:
    enabled:
      - oid4vc-vci
      - oid4vc-vci-preauth-code        # KC 26.4+: gates the pre-authorized_code grant
      - oid4vc-vci-rest-credential-offer  # KC main / SEAMWARE 26.6.3: gates /create-credential-offer

    Without oid4vc-vci-rest-credential-offer, Keycloak answers any call to /protocol/oid4vc/create-credential-offer with 403 invalid_client: "REST credential offer functionality is not enabled". The flag is defined in Profile.Feature.OID4VC_VCI_REST_CREDENTIAL_OFFER and is consumed by OID4VCIssuerEndpoint.checkRestCredentialOfferEnabled. It landed in upstream main together with the OID4VCI QR-generation fix and is present in the patched quay.io/seamware/keycloak:26.6.3 image shipped by the umbrella, even though vanilla 26.6.2 does not carry it.

    The umbrella ships these three defaults out of the box.

    Endpoint changes for custom wallets / scripts¶

    If you have custom code that talks to the Keycloak OID4VCI endpoints, update it as follows:

    Step Old (KC 26.3) New (KC 26.4 → 26.6.2) Newer (KC main / SEAMWARE-patched 26.6.3)
    Request offer URI GET /protocol/oid4vc/credential-offer-uri?credential_configuration_id=X GET /protocol/oid4vc/create-credential-offer?credential_configuration_id=X&pre_authorized=true same
    Build offer URL ${issuer}${nonce} ${issuer}/${nonce} same
    /credential body {"credential_identifier":"X","format":"jwt_vc"} {"credential_configuration_id":"X"} {"credential_identifier":"<id-from-token-response>"}
    /credential response {"credential":"<jwt>"} {"credentials":[{"credential":"<jwt>"}]} same
    credential_identifier source n/a (anything accepted) n/a must come from the authorization_details[].credential_identifiers array returned by /token after exchanging the pre-authorized code

    The pre_authorized query parameter on /create-credential-offer defaults to false, so it must be set explicitly to obtain the pre-authorized_code grant. The format field of /credential is no longer accepted as input — format selection happens by picking a credential_configuration_id whose configured vc.format matches what the caller expects.

    credential_identifier flow (keycloak/keycloak#47404)¶

    The patched 26.6.3 image arrives with the upstream rule that /credential only accepts a credential_identifier, never a credential_configuration_id. The identifier is short-lived and bound to the issued access token:

    1. Wallet exchanges the pre-authorized code at /token.
    2. /token response contains: 
      "authorization_details": [{
  "type": "openid_credential",
  "credential_configuration_id": "user-credential",
  "credential_identifiers": ["user-credential_0000"]
}]
    3. Wallet POSTs /credential with {"credential_identifier": "user-credential_0000"}.

    Sending the legacy {"credential_configuration_id": "..."} body against this image returns 400 invalid_credential_request: "Credential must be requested by credential identifier from authorization_details: [...]".

    The IT framework's Wallet.java was updated accordingly: it reads authorization_details off the TokenResponse model and falls back to the previous credential_configuration_id-based body when the field is absent, so it still works against older Keycloak versions.

    Client roles consistency¶

    KC 26.4+ rejects user→client role assignments where the client itself does not declare the role. The realm import attempts to auto-create the missing role and, if multiple users assign it in the same batch, fails with duplicate key violates unique constraint.

    Required action:

    For every clientRoles.<clientId>: [...] you set on a user, declare the same role under realm.clientRoles.<clientId>. The consumer.yaml and provider.yaml example overlays in this repository show the consistent shape (REPRESENTATIVE declared on did:web:mp-operations.org, seller/admin declared on did:web:fancy-marketplace.biz).

    Per-user verifiableCredentials assignment¶

    KC main (carried by the SEAMWARE-patched 26.6.3 image — see keycloak/keycloak@6ef5a79) ties /create-credential-offer to a per-user verifiableCredentials list. A user that has not been explicitly granted a credential gets:

    400 invalid_credential_offer_request
"User 'X' does not have verifiable credential 'Y'."

    even with a valid token and a properly configured ClientScope.

    In the realm import JSON the list lives on each user entry:

    {
  "username": "employee",
  "verifiableCredentials": [
    { "credentialScopeName": "user-credential" },
    { "credentialScopeName": "operator-credential" }
  ]
}

    Required action:

    Either set this list per user, or set the chart flag below to have the umbrella auto-assign every VC declared in the realm to every user that has not provided its own verifiableCredentials:

    keycloak:
  realm:
    wallets:
      issueCredentialsToUsers: true

    wallets.enabled does not need to be true for this to work — the two flags are independent. The local k3s overlays (k3s/consumer.yaml, k3s/provider.yaml) ship with issueCredentialsToUsers: true so the example deployment works out of the box; in production you usually want to declare the per-user lists explicitly instead.

    OID4VCI draft compliance¶

    Keycloak 26.6.3 implements OID4VCI Draft 15. The 26.4 redesign (keycloak/keycloak#39768) explicitly aligned the credential issuance flow with Draft 15: CredentialSubject was removed from CredentialDefinition, the format field was dropped from CredentialRequest, the metadata endpoint claims structure was rewritten and the cwt proof type was removed.

    Practical implications already covered above (see Endpoint changes for custom wallets / scripts, OID4VCI realm model rewrite and Format strings rename):

    • /credential request: send credential_configuration_id (no format); response is {"credentials":[…]}.
    • /credential-offer-uri is replaced by /create-credential-offer?pre_authorized=true.
    • Format strings updated: jwt_vc → jwt_vc_json, vc+sd-jwt → dc+sd-jwt.

    If you maintain a custom wallet or test harness, target Draft 15 endpoints and payloads.

    Credential request/response encryption (JWE)¶

    Keycloak 26.6.x advertises OID4VCI credential encryption in the issuer metadata (/.well-known/openid-credential-issuer). Two independent features are involved, and both have caused interop failures with wallets that encrypt:

    Request encryption (credential_request_encryption). Advertised whenever the realm has an asymmetric encryption key — the chart ships one via the ecdh-generated key provider in keycloak.realm.defaultKeyProviders (ECDH-ES, P-256). A wallet that encrypts the /credential request must include the issuer key's kid in the JWE header; otherwise Keycloak answers 400 invalid_encryption_parameters with Request has JWT content-type but is not a valid JWE: Missing kid in JWE header. The EUDI eudi-lib-ios-openid4vci-swift omitted the kid before 0.38.3 (fixed by "add kid to header on issuance").

    Response encryption (credential_response_encryption). Advertised whenever the realm has any asymmetric key — if the ecdh-generated key is removed it simply falls back to RSA-OAEP via the realm's RSA token-signing key. A wallet requesting an encrypted response must not send alg at the top level of the credential_response_encryption object: Keycloak's model only accepts {zip, enc, jwk} and otherwise fails with Unrecognized field "alg" (class CredentialResponseEncryption). eudi-lib-ios-openid4vci-swift sent the top-level alg before 0.40.0 (fixed by "Remove alg from top level").

    Guidance:

    • Wallets that opt into encryption need eudi-lib-ios-openid4vci-swift ≥ 0.40.0 (carries both fixes). Lissi does not encrypt the request/response, so it is unaffected.
    • There is no realm/chart toggle to stop advertising credential_response_encryption: it is inherent to KC 26.6.x and the RSA signing key cannot be removed. Removing the ecdh-generated key provider only neutralises request encryption (the section disappears from the metadata); response encryption stays advertised but is optional (encryption_required: false), so a wallet that does not request it is unaffected.

    Operational notes & gotchas¶

    Reusing an existing Keycloak database (USER_VER_CREDENTIAL migration)¶

    The post-26.4 OID4VCI model ties /create-credential-offer to a per-user verifiableCredentials list, backed by a custom USER_VER_CREDENTIAL table. Pointing 26.6.x at a database created by an older Keycloak fails at offer time with:

    ERROR: column uvce1_0.version does not exist
  at org.keycloak.protocol.oid4vc.utils.OID4VCUtil.hasVerifiableCredential

    The shipped quay.io/seamware/keycloak:26.6.3 image carries the Liquibase changeset 26.7.0-verifiable-credential, which adds the missing version column on startup. Use 26.6.3 (not 26.6.2) when reusing a database.

    Related: Keycloak does not re-import an already-existing realm. Changes under keycloak.realm.* do not take effect on a running realm — delete and recreate the realm (the external DB makes this safe) for the new import to apply.

    DCQL query format gotchas¶

    For Credentials Config Service / VCVerifier scopes that use DCQL (oidcScopes.<scope>.dcql):

    • meta.type_values (W3C jwt_vc_json) is an array of string arrays, e.g. [["MarketplaceCredential"]] — a flat array is rejected with cannot unmarshal string into ... type_values of type []string.
    • meta.vct_values (SD-JWT dc+sd-jwt / vc+sd-jwt) is a flat array of strings, e.g. ["LegalPersonCredential"].
    • credential_sets must be a non-empty array. A nil credential_sets serialises to JSON null, which the SwiftyJSON parser in the Lissi/EUDI wallets rejects with "JSON is invalid". For dual-format offers, list both credential ids as alternatives: credential_sets: [{ options: [["lpc-dc-sd-jwt"], ["lpc-vc-sd-jwt"]], required: true }].

    StatefulSet recreation when upgrading from 9.x (Bitnami → CloudPirates)¶

    The Bitnami and CloudPirates keycloak charts both name the workload <release>-keycloak, but their StatefulSet specs differ in immutable fields (serviceName, selector, volumeClaimTemplates). An in-place upgrade fails with updates to statefulset spec for fields other than ... are forbidden. Delete the old StatefulSet so it is recreated — kubectl delete statefulset <release>-keycloak (the external Postgres means no data loss; the pod is stateless).

    Migration checklist¶

    1. Apply the value renames in the table above to your keycloak: block; remove the listed obsolete keys.
    2. Rewrite each entry under keycloak.realm.attributes of the form vc.<name>.* as a keycloak.realm.verifiableCredentials.<name> block with attributes and protocolMappers. Drop the keycloak.realm.credentialBuilder: block entirely.
    3. Update format strings: vc+sd-jwt → dc+sd-jwt, jwt_vc → jwt_vc_json, both in the realm config and in any DCQL queries you maintain.
    4. If you override keycloak.realm.defaultClients, preserve account-console.attributes.oid4vci.enabled: "true".
    5. Add oid4vc-vci-preauth-code to keycloak.features.enabled.
    6. Update any custom wait-for-keycloak probe to target <release>-keycloak-metrics:9000.
    7. Validate locally with helm template charts/data-space-connector -f your-values.yaml and a one-off kc.sh import --dir=/opt/keycloak/data/import against a 26.6.3 pod before redeploying.
    8. Rerun your integration tests; confirm both consumer and provider Keycloaks reach Listening on http://0.0.0.0:8080 and that VC issuance flows complete.

    For a worked end-to-end example, see the migrated k3s/consumer.yaml and k3s/provider.yaml overlays shipped with this release; the oid4vc-protocol-mappers.md reference now documents the 26.6.3 mapper API.

    EDC / Dataspace Protocol production readiness¶

    The EDC part of the chart could be deployed but not operated: everything that keeps a participant's identity alive lived outside the chart, and several pieces broke on their own with no deployment involved. This release closes that.

    Participant provisioning is part of the chart¶

    A deployed identityhub used to be inert - no participant context, no signing key in Vault, no credential - and the documented way to fix that was a curl sequence run from a workstation, which every real deployment reimplemented as a hand-written Job. identityhub.bootstrap now performs it in-cluster and idempotently, on install and on every upgrade.

    identityhub.bootstrap.keyAlias string key-1 Vault alias and DID fragment of the signing key
    identityhub.bootstrap.credentialServiceUrl string "" Public base URL of the DCP credential service

    post-upgrade is part of the default hook and needs to stay there while Vault runs in dev mode: its storage is in-memory, so every Vault restart drops the signing key, the super-user credential and the STS client secret, and only a re-run restores them.

    The identityhub credential no longer goes stale on its own¶

    The identityhub holds its own copy of the credential a connector presents, and nothing kept it in step: the vc-operator renewed the Secret while the identityhub went on presenting the previous credential until it expired, taking the DCP lane down with a Secret that looked perfectly healthy.

    identityhub.credentialSync.enabled renders a sidecar in the identityhub pod that mirrors the Secret the vc-operator maintains into the identityhub's credential store, on issuance and on every renewal. It needs the Secret's name (identityhub.credentialSync.secretName) and the super-user api key in a Secret (identityhub.superuser.existingSecret).

    The sidecar writes over localhost: the Identity API is component-internal, so the only thing that writes to it is the pod that owns the store. Obtaining and renewing the credential stays with the vc-operator, which never talks to the identityhub.

    identityhub.bootstrap.credential.* is deprecated in favour of it and still read as a default: storing the credential is not a bootstrap concern, since a Job that only runs on install and upgrade leaves the copy stale after the first unattended renewal. The bootstrap Job no longer stores it.

    Related: identityhub.credentialWatchdog.checkPeriodSeconds now exposes the identityhub's own watchdog, which re-requests expiring credentials from a DCP issuer service. It defaults to 0 (off), because the credentials here come from an OID4VCI issuer and there is no issuer service to ask; upstream defaults it to 60 seconds with a one-week renewal grace period, which for a credential that only lives a week means it is considered renewable from the moment it is issued.

    Also consider raising renewBefore from the 5m default: five minutes leaves no room to notice a failure before the credential in use expires.

    vault.hashicorp.token is rendered into ConfigMaps in clear, so anyone able to read ConfigMaps in the namespace can read the credential that unlocks the participant's signing key. With existingSecret the identityhub receives it as EDC_VAULT_HASHICORP_TOKEN and the property is omitted from the ConfigMap entirely.

    A Vault with persistent storage comes back sealed after every restart, so persistence alone is not enough; vault.unattended initialises an empty Vault once and unseals it whenever it finds it sealed, and mints the scoped token the components authenticate with.

    The name is deliberate: this is not a production security posture. A Vault that unseals itself keeps its unseal keys in a Secret of the same namespace, so whoever can read Secrets there can open it. It is the right trade for demo and staging, where the alternative - dev mode - loses the participant's identity on every restart and does not put it back until the next deploy, because the bootstrap Job is a Helm hook and not a restart hook.

    Production is autoUnseal: false: no unsealer is deployed, the operating organisation holds the key shares, and a quorum unseals on every start. That step cannot be automated away. Both variants, including the one-off init and the per-start procedure, are in the production guide.

    vault.unattended.enabled refuses to render next to vault.server.dev.enabled rather than quietly doing nothing.

    Rotating the signing key¶

    identityhub.bootstrap.rotation replaces the identity key while keeping the same Vault alias and the same DID fragment, which is what keeps the Keycloak realm out of it - signing_key_id is a ClientScope attribute and cannot be changed by automation on an existing realm.

    There is no overlap window. The moment the key is replaced, everything signed with the previous one under that fragment stops verifying, credentials already in wallets included, so re-issuance is part of the operation. The Job is opt-in and never a Helm hook. The runbook is in the production guide.

    Note also that cert-manager's privateKey.rotationPolicy defaults to Always since cert-manager 1.18, i.e. renewing a certificate generates a new key, which invalidates the published DID document. Declare rotationPolicy: Never explicitly for the identity key.

    Fixes¶

    • vc.expiry_in_seconds and vc.refresh_interval_in_seconds are kept in sync. The admin console shows the first while the issued exp comes from the second, so setting only one produced credentials expiring at a completely different time than the console claimed - with Keycloak's default, a week instead of whatever was configured. Setting neither still leaves Keycloak's defaults alone.
    • vc.signing_key_id defaults to the key id the DID document publishes when the identityhub serves that document. Keycloak otherwise defaults it to the bare DID, which is not resolvable there, and issuance fails with No key for id '<did>' and algorithm ... available.
    • The trusted-issuers registration script treats a 409 as success. It used curl -f, so an already-registered issuer failed the Job - which is why making it run on upgrade required this fix first.
    • identityhub.customCaCerts works. The deployment mounted an empty emptyDir over the JVM truststore and referenced a ConfigMap nothing created, so declaring extra CAs replaced the whole truststore with nothing. An init container now imports them into a copy of it.
    • identityhub.customCaCertsFrom takes CAs from Secrets and ConfigMaps that already exist, so a cert-manager Secret can be pointed at instead of having its PEM copied into values. Sources are merged with a projected volume and a deployment that uses only this key renders no ConfigMap at all. Secrets default to ca.crt: mounting a kubernetes.io/tls Secret whole would put tls.key in the pod and fail the import.
    • identityhub.logging.persistence is gone. It mounted a claim that nothing created, so enabling it produced a pod that could never be scheduled. Rather than add the missing claim, the option was removed: the file handler writes to an emptyDir and the console handler is what feeds the cluster's log stack, which is where logs belong.
    • The identityhub service exposes the accounts port (8085) that the deployment opens, so the STS Accounts API is reachable in-cluster.

    helm unittest gained suites covering the bootstrap, the credential-sync sidecar, the unattended Vault surface and the holder key id cross-check, and .github/scripts/eval.sh now renders each chart's ci/*-values.yaml in addition to its defaults.     Consent management¶

    The connector can now record and enforce consent (ISO/IEC TS 27560) on a data path, opt-in via the consent maven profile. A data subject's personal data is released to a consumer only while that subject has a granted consent for it.

    Three components carry it, each deployed from its own published FIWARE chart:

    component chart runs at
    consent-manager oci://quay.io/fiware/helm-charts/consent-manager the authority (trust-anchor release)
    consent-facade oci://quay.io/fiware/helm-charts/consent-facade the authority, plus a provider-local instance
    consent-owner-resolver oci://quay.io/fiware/helm-charts/consent-owner-resolver the provider

    Enforcement itself is an APISIX external plugin (consent-filter) on the provider's mp-data-service-consent route: OPA authorizes the request on the presented credential, then the plugin asks the owner-resolver whose data was returned and checks that owner's consent at the consent-manager - so the decision is made from the data, not from whoever requested it.

    Participants and data subjects authenticate over OID4VP throughout; no component holds a participant client secret, and the shared consent key is injected by the authority's APISIX facade rather than handed to callers.

    See Consent Management for the architecture, the enabling overlays and two end-to-end walkthroughs.

    contract-management 3.3.12 requires trusted-issuers-list >= 0.9.0¶

    contract-management now registers the credentials of a newly onboarded participant through PUT /issuer/{did}/credential?scope=<product-order-id>, an endpoint that only exists from trusted-issuers-list 0.9.0 on.
